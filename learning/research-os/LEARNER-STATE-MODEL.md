# Research OS for K-12: The Learner State Model

**Status:** draft, bead `ros-02` · **Date:** 2026-09-10 · Reads against `learning/research-os/PLAN.md` section 2, `PLAN-REVISION-1.md` sections 2 and 3 item 1, `RESEARCH-QUESTIONS.md`, `_intake/research-os-k12/RESEARCH-OS-K12-SYSTEM-REVIEW.md` section 3, `src/lib/research-os/stages.ts`, `src/lib/research-os/probe.ts`, `src/lib/research-os/types.ts`, `supabase/migrations/20260910000000_research_os_graph.sql`, `learning/EPIC.md`, and `src/lib/academy/mastery.ts`.

Every later Research OS outcome claim depends on this paper. A study that reports "learners at Internalization retained more than learners at Understanding" is only meaningful if Internalization names one measurable thing, distinct from Understanding, that a second rater would classify the same way. This paper states what each of the five states means as an operational test, maps that test against five external frameworks so a reader outside Bucket can place it, maps it against what `src/lib/research-os/stages.ts` ships today, and names the measurement plan and the logging gaps a pilot study needs closed before item 1 of `RESEARCH-QUESTIONS.md` can run.

## 1. The five states, defined operationally

A state describes a learner's relationship to one graph node (`graph.nodes`), stored per `(learner_id, node_id)` in `graph.learner_node_state.stage` (`supabase/migrations/20260910000000_research_os_graph.sql`). Two properties hold across all five states, both by construction in `src/lib/research-os/types.ts` and `stages.ts`: `stage` is a high-water mark, `stageAtLeast` and every transition function only ever raise it, never lower it; and every transition appends one event to `graph.learner_node_state.evidence` before, or instead of, changing `stage`, so the append-only log is the audit trail a contest or a second rater reads.

| State | Entry condition | Evidence that satisfies it | Judge | Decay rule |
|---|---|---|---|---|
| Access | Every prerequisite of this node is at Understanding or above in the learner's own state, computed by the router at request time | Membership in `computeFrontier`'s reachable set (`src/lib/research-os/frontier.ts`, comment: "treat no record as access"); no database row need exist yet | System, a graph computation, no model call | None. Access is recomputed fresh on every route request and never stored, so nothing decays |
| Awareness | The learner opened the node | One `open` evidence event (`stages.ts` `onNodeOpened`) | System, a client event, no model call | None stored. `stage` is monotonic; PLAN.md section 2's original table names live FSRS retrievability as the intended decay signal for this state; section 3 below shows this remains unimplemented in `src/lib/research-os` |
| Understanding | The learner wrote a free-text explanation and the Check tool judged it grounded | One `check` evidence event with `result: "support"`, `confidence` above `"low"`, and `abstained: false` (`stages.ts` `onCheckResult`, gated on the row already being at Awareness or above) | System plus a language model: `src/lib/research-os/grounding.ts` `gradeExplanation`, an LLM-judge call every time, with no deterministic branch implemented in this codebase today | None stored, same gap as Awareness |
| Internalization | The learner answered a transfer item, and a teacher approved the hold | Two evidence events: a held `transfer_item` event that never advances `stage` on its own (`onTransferItemAnswered`), followed by a `teacher_review` event with `decision: "approved"` (`onTeacherReview`), which is the one transition in this file that raises `stage` | Teacher, required. No transfer item in this codebase can advance a learner past Understanding by itself | None stored, same gap |
| Production | The learner submitted a production for this node | One `production_submitted` evidence event (`onProductionSubmitted`), unconditional | System, at the moment of submission; acceptance is a separate, later judgment | See the note below: submission and acceptance are two different judgments, and only one of them is reflected in `stage` |

### Access

Access is the one state with no row required. `frontier.ts`'s backward walk treats a node with no `learner_node_state` record as Access, and the router's job stops there: Access only asks whether a path to this node exists at all; whether the learner has taken that path is a separate question, answered by the states below. This matches the system review's "prerequisites unlocked, content exists in the learner's language, device tier can render it, age gating passes... Binary eligibility check, no AI call" definition, with the K-12-specific gates (language, device, age) not yet built into the Phase 0 router, which checks prerequisite stage alone.

### Awareness

Awareness fires the moment a learner opens a node, one client-reported `open` event, no model call, no correctness judgment at all. This is a much thinner bar than PLAN.md section 2's original table, which named "FSRS retrievability above the Academy recall threshold" as the Awareness signal. What shipped in `stages.ts` is the Phase 0 simplification: opening a node is treated as sufficient evidence of Awareness, and the retrievability-based version PLAN.md described has no implementation in `src/lib/research-os` (verified: no file under `src/lib/research-os/` or `src/app/api/research-os/` references `retrievability`, `stability`, or `fsrs`). Section 3 below treats this as the load-bearing shipped-versus-planned gap for this state.

### Understanding

Understanding is the first state a model judges. The learner submits a free-text explanation; `gradeExplanation` grounds the verdict against the node's own `summary` and its prerequisites' summaries only, never outside knowledge, and returns `support`, `contradiction`, or `unknown` plus a qualitative confidence. `onCheckResult` raises `stage` to Understanding only when the result is `support`, confidence is not `low`, and the model did not abstain. The system review's ideal design promises "deterministic where possible... falling back to an LLM-judge pass when no deterministic check applies"; the shipped Check tool has no deterministic branch, every Understanding judgment is an LLM call. Academy's own deterministic grading (SymPy symbolic equivalence, `learning/EPIC.md` Phase 2) exists as a design commitment for the Academy credential path but is not wired into the Research OS Check tool.

### Internalization

Internalization is the only state gated on a human by construction, with no code path that lets a model or the learner's own answer move it. `onTransferItemAnswered` logs the attempt and explicitly leaves `stage` unchanged, its own comment names this "teacher_judgment_stub" and points at Phase 1. `onTeacherReview` is what raises the stage, and only when the decision is `"approved"` and the row is already at Understanding and not yet at Internalization. A `"returned"` decision requires a one-line reason (enforced in `src/app/api/research-os/review/route.ts`) and leaves the learner at Understanding with the reason logged.

### Production

Production is set at submission, the moment `graph.productions` gets a new row, before any reviewer has looked at it, and this timing is a real property of the shipped code, confirmed by reading the code rather than assumed from the plan. `onProductionSubmitted`'s own comment states the design choice directly: "Unlike the internalization gate above, task item 5 lists this transition without a stub caveat." Acceptance is tracked separately, on `graph.productions.status`, which moves `draft` to `submitted` to `accepted` or `returned` through `POST /api/research-os/review` with `kind: "production"`. Reading `src/app/api/research-os/review/route.ts`'s production branch line by line: an accepted or returned decision updates `graph.productions.status` and inserts one `graph.teacher_reviews` row, and never touches `graph.learner_node_state`. A returned production leaves the learner's `stage` at `production` with no correcting evidence event, a real logging gap named again in section 4. PLAN.md section 2's own definition of Production, "the learner has produced a claim with evidence and citations that reviewers accepted into the graph," describes the reviewed-and-accepted state; `stage: "production"` today verifies only that a submission happened. Any outcome measure that treats `stage: "production"` as evidence of an accepted, citable claim has to additionally filter on `graph.productions.status = "accepted"`.

## 2. Mapping to external frameworks

Each table below reads the Bucket state on the left against its closest counterpart in one external framework, with a fit note. A blank counterpart cell means the framework draws no distinction at that point; the prose after each table says why that gap is real rather than a naming mismatch. Every citation below is DOI- or ISBN-verified and carries an intake card under `_intake/research-os-k12-literature/educational-methods/`.

### ICAP

Chi and Wylie 2014, "The ICAP Framework: Linking Cognitive Engagement to Active Learning Outcomes," *Educational Psychologist* 49(4), 219 to 243, doi:10.1080/00461520.2014.965823 (`_intake/research-os-k12-literature/educational-methods/chi-wylie-2014-icap-framework.md`). ICAP orders four modes of engagement with material, Passive, Active, Constructive, Interactive, by the cognitive processing each is argued to produce, with Interactive predicted to beat Constructive, Constructive to beat Active, and Active to beat Passive.

| Bucket state | ICAP counterpart | Fit |
|---|---|---|
| Access | No counterpart | ICAP classifies engagement with material already being attended to; Access precedes any engagement and has no ICAP analogue |
| Awareness | Passive | Opening a node with no generative or manipulative act matches ICAP's Passive mode, receiving information with no observable added behavior |
| Understanding | Constructive | Writing a free-text explanation the Check tool must ground is a generative act beyond selecting or manipulating given material, ICAP's Constructive criterion |
| Internalization | Constructive, moving toward Interactive when the scripted peer step (PLAN.md section 3) ships | A transfer item answered alone stays Constructive; PLAN.md's planned frontier-node peer step would add an Interactive component ICAP predicts should outperform solo Constructive work, untested in the shipped code |
| Production | Interactive | A production reviewed and accepted into a shared graph, later cited by other learners and by the hypothesis engine, is dialogue with the graph's other users over time, ICAP's Interactive criterion |

ICAP's four modes are argued to be ordered by observable behavior alone, with no claim that a five-way split adds predictive power beyond the four. RQ1 in `RESEARCH-QUESTIONS.md` is written to test exactly this: whether Bucket's five states predict delayed transfer beyond ICAP mode, or restate it under new names. Access has no ICAP counterpart because ICAP begins after a learner has already engaged with content; Bucket adds Access as the reachability gate a school-age learner needs that an adult autodidact with an open browser tab does not.

### SOLO

Biggs and Collis 1982, "Origin and Description of the SOLO Taxonomy," in *Evaluating the Quality of Learning: The SOLO Taxonomy*, Academic Press, doi:10.1016/b978-0-12-097552-5.50007-7, ISBN 978-0-12-097552-5 (`_intake/research-os-k12-literature/educational-methods/biggs-collis-1982-solo-taxonomy.md`). SOLO orders the structural complexity of one response to one task: prestructural, unistructural, multistructural, relational, extended abstract.

| Bucket state | SOLO counterpart | Fit |
|---|---|---|
| Access | No counterpart | SOLO scores a produced response; Access precedes any response |
| Awareness | Prestructural to unistructural | Recognizing and opening a node with no explanation attempt sits below SOLO's unistructural level, which already requires one relevant element used |
| Understanding | Multistructural to relational | A grounded explanation that connects the node to its prerequisites, which Check's grounding prompt requires, reaches SOLO's relational level, several disconnected facts integrated into a coherent whole |
| Internalization | Relational to extended abstract | A transfer item applied to an unseen scenario is SOLO's extended abstract move, generalizing a relational structure to a new domain |
| Production | Extended abstract, with a further step SOLO does not name | Contributing a new, cited claim to a shared graph others build on is beyond SOLO's own ceiling; SOLO scores the complexity of a response to a given task, and adding a new node to the structure other people's tasks will later reference is a further act SOLO was never built to score |

SOLO is a within-response coding scheme, built to grade one essay or one problem solution at a time; tracking a learner's trajectory across many encounters with the same idea over time, the way `stage` does, is a use SOLO's own design never addressed. Section 3's RQ28 (Rasch or IRT fit) borrows SOLO's own claim to unidimensionality as the test the five states have to clear before they can be scored the way SOLO scores are scored.

### Bloom revised

Anderson, Krathwohl, and others, *A Taxonomy for Learning, Teaching, and Assessing: A Revision of Bloom's Taxonomy of Educational Objectives*, Longman, 2001, ISBN 978-0-8013-1903-7 (`_intake/research-os-k12-literature/educational-methods/anderson-krathwohl-2001-taxonomy-revision.md`). The revision crosses six cognitive processes, Remember, Understand, Apply, Analyze, Evaluate, Create, against four knowledge types, factual, conceptual, procedural, metacognitive.

| Bucket state | Bloom revised counterpart | Fit |
|---|---|---|
| Access | No counterpart | The revision starts at Remember, retrieving relevant knowledge; Access precedes retrieval entirely |
| Awareness | Remember | Opening a node with no further act matches Remember's retrieval-only bar |
| Understanding | Understand, reaching into Apply | A self-generated explanation the Check tool grounds against source material sits at Understand's "explaining" cognitive process, and edges into Apply when the explanation is cast in the learner's own worked terms |
| Internalization | Apply, reaching into Analyze | A transfer item on unseen material is squarely Apply's "executing or implementing in a new situation"; a multi-hop transfer item that draws on several graph nodes at once reaches Analyze's "differentiating and organizing" |
| Production | Create | Producing a claim, with evidence, that a reviewer accepts as a new addition to the graph is Create's own definition, "putting elements together to form a novel, coherent whole" |

Bloom revised's taxonomy crosses process against knowledge type in a two-dimensional grid; Bucket's `stage` collapses both into one ordinal column. A five-state model that separately tracked which knowledge type (factual, conceptual, procedural) a learner has reached at Understanding, rather than treating "Understanding" as one undifferentiated bucket, would be closer to what Bloom revised specifies. That refinement is not built and is named as OPEN-3 below.

### Perkins's understanding performances

Perkins, David, "Teaching for Understanding," *American Educator* 17(3), 8, 28 to 35, Fall 1993, ISSN 0148-432X, ERIC EJ473811, and Wiske, Martha Stone, editor, *Teaching for Understanding: Linking Research with Practice*, Jossey-Bass, 1998, ISBN 978-0-7879-1002-0 (`_intake/research-os-k12-literature/educational-methods/perkins-1993-teaching-for-understanding.md` and `_intake/research-os-k12-literature/educational-methods/wiske-1998-teaching-for-understanding.md`). This framework defines understanding as a flexible performance capacity, the ability to think and act with a topic in ways that go beyond stored information, tested through generative topics, throughlines, understanding goals, understanding performances, and ongoing assessment.

| Bucket state | Perkins counterpart | Fit |
|---|---|---|
| Access | No counterpart | Perkins's framework begins once a learner is engaging a generative topic; Access is the reachability gate before that |
| Awareness | Below Perkins's own floor | Perkins treats "possession of information" as a prerequisite for understanding, a floor a learner clears before understanding begins; Awareness sits at exactly that pre-understanding floor |
| Understanding | One understanding performance, explanation | Perkins names several performance types, explanation, exemplification, application, justification, comparison and contrast, contextualization, generalization; the shipped Check tool tests explanation only |
| Internalization | A second understanding performance, application to an unfamiliar case | A transfer item drawn from a sealed pool and applied to a scenario never seen matches Perkins's application performance directly |
| Production | Beyond Perkins's own list | A reviewed, citable, graph-accepted contribution is a stronger claim than performing understanding for an assessor; it requires convincing an external reviewer using evidence, closer to a scholarly claim than a classroom performance |

Perkins's framework names several understanding performances; the shipped Understanding and Internalization stages test two of them, explanation and application to a novel case. Justification, comparison and contrast, and generalization have no dedicated Bucket signal today, which is RQ4's own question, "does the Production state show transfer to unfamiliar formats or format-matched performance only," restated at the Understanding and Internalization level rather than only at Production.

### The founder's three-level model

Awareness, Explainable understanding, Internalized understanding is the founder's working model that predates the five-state design and is not written down in any file in this repository; it is recorded here from the bead brief itself as the direct precursor the five states expand.

| Founder's tier | Bucket state | Fit |
|---|---|---|
| Awareness | Awareness | Direct one-to-one match; the founder's own naming survived unchanged into the shipped `Stage` enum |
| Explainable understanding | Understanding | The founder's tier names the ability to explain a concept in one's own words; the shipped Check tool tests exactly that ability, so this is close to a direct match, though the founder's tier was never operationalized into a pass and fail rule the way `onCheckResult`'s grounded-support-and-not-low-confidence test now is |
| Internalized understanding | Internalization | Close match in name and intent, "holds and transfers over time" is the founder's own phrase for this tier and PLAN.md section 2 repeats it verbatim for Internalization; the transfer-item-plus-teacher-approval mechanism that operationalizes it is new relative to the founder's original informal tier |

The five-state model adds Access below the founder's three tiers and Production above them; it does not split any of the founder's three tiers into two. Access answers a K-12-specific problem the founder's original model, built around an adult autodidact who chooses their own material, never had to answer: whether a learner is even allowed to see this node yet. Production answers a different K-12-specific problem: whether school-age production of new knowledge can be credentialed and cited the way the founder's adult Mastery Profile already credentials mastery. Because the founder's three-level model is an informal working framework rather than a published instrument, no paper poses a validation question against it directly; OPEN-5 below poses the closest available version of that question using a published measurement-theory source instead.

## 3. Mapping to the shipped Academy ladder and to FSRS, IRT signals

### The Recall-Apply-Derive-Teach ladder

`src/lib/academy/mastery.ts` infers a learner's depth on the Recall, Apply, Derive, Teach ladder from `inferDepth`, which reads fused mastery (`fusedConceptMastery`, proficiency raised to the alpha power times retention raised to the beta power) against fixed thresholds, `mastery < 0.25` targets Recall, `< 0.5` targets Apply, `< 0.75` targets Derive, and above that targets Teach, capped to whichever depth the atom's own quiz metadata can test. PLAN.md section 2's state table already names the intended pairing, Awareness reuses Recall, Understanding reuses Apply, Internalization reuses Derive, Production reuses Teach, Access has no Academy depth equivalent.

| Bucket state | Academy depth | What connects them today |
|---|---|---|
| Access | none | No connection; Access is Research OS-only |
| Awareness | Recall | Conceptual pairing only. No code path reads an Academy `mastery.ts` value to set a Research OS `stage`; the two systems run on separate tables (`graph.learner_node_state` versus `bucket.academy_progress`) with no join between them |
| Understanding | Apply | Same, conceptual pairing only, no shared code or shared table |
| Internalization | Derive | Same |
| Production | Teach | Same. Teach-back in Academy means explaining a concept to a simulated learner inside the mastery ladder; Production in Research OS means a reviewed, citable claim entering the graph. The two "Teach" and "Production" concepts share a name-level intuition, contributing knowledge outward, and share no implementation |

### FSRS and IRT proficiency, as shipped

Verified by search: no file under `src/lib/research-os/` or `src/app/api/research-os/` references `retrievability`, `stability`, `fsrs`, `theta`, or `proficiency`. The formula `M = P^alpha * R^beta` that fuses IRT/Elo proficiency with FSRS retention (`src/lib/academy/mastery.ts` `fuseMastery`, mirroring `learning/app/js/adaptive.js`) governs the Academy Mastery Profile only. Research OS's own transitions run on three signals instead, an `open` client event, a Check tool verdict, and a teacher decision, none of which is FSRS retrievability or IRT theta.

A join is possible without a schema change, because it is not impossible, only unbuilt: `src/lib/research-os/ingest/academy.ts`'s `academyNodeSlug` builds every imported node's `graph.nodes.slug` as `academy-<source-file>-<atom-id>`, which is a deterministic, reversible encoding of the Academy atom id the node came from. `bucket.academy_progress` stores one row per `(user_id, branch)` with a `data` jsonb blob keyed by that same atom id (`cards[atomId]`, `prof[atomId]`). Reading a learner's FSRS retrievability for a Research OS node today would require parsing the node's own slug to recover `(sourceFile, atomId)`, mapping the source file to a branch, reading that branch's `bucket.academy_progress` row, and indexing into its `cards`/`prof` blob by atom id, a four-step, string-parsing bridge that exists nowhere in the codebase. This is the concrete shape of the gap PLAN.md section 2's Awareness row ("FSRS retrievability above the Academy recall threshold") describes and `stages.ts` does not implement; section 4 below lists it as a logging and wiring gap, not only a documentation one.

### What the diagnostic probe sets

`src/lib/research-os/probe.ts`'s `buildProbe` fires only when a learner has no state record on any ancestor of a routing target, the cold-start case system review section 3 step 5 names. `onProbeCheckResult` (`stages.ts`) grades a probe answer with the same `gradeExplanation` call Check uses, but scores the result differently from an in-path Check, because a cold-start probe answer means something different from an answer given after opening the node:

- A non-abstained support result at or above medium confidence jumps directly to Understanding, skipping the Awareness gate `onCheckResult` enforces, since the probe deliberately reaches a node the learner never opened.
- A non-abstained support or unknown result below that confidence bar sets Awareness, some prior familiarity shown, short of a full explanation.
- A contradiction, or an abstained result, stays at Access, though the attempt is still logged as evidence either way.

### What a teacher review sets

Two review kinds share `POST /api/research-os/review`. A `transfer_item` review with `decision: "approved"` runs `onTeacherReview`, which raises Understanding to Internalization when the row is already eligible, and writes one `teacher_review` evidence event onto `graph.learner_node_state.evidence` in addition to the audit row in `graph.teacher_reviews`. A `production` review only ever updates `graph.productions.status`, between `submitted` and `accepted` or `returned`; it never calls `recordEvidence`, so no teacher decision on a production ever appears in `graph.learner_node_state.evidence`, and, as section 1 states, a returned production leaves `stage` at `production` uncorrected.

### What a Production sets

`onProductionSubmitted` sets `stage` to `production` unconditionally at the moment `graph.productions` gets a new row for this node, independent of review outcome. The production's own credential-worthiness, whether it is citable, whether the engine can ingest it, lives entirely on `graph.productions.status`, gated to `accepted` by the review flow above and never mirrored back onto `stage`.

## 4. Measurement plan for the three-arm pilot

`PLAN-REVISION-1.md` section 4 names the three-arm testbed, constrained workspace, permissive tutor, no-AI control, as the direct instrument for `RESEARCH-QUESTIONS.md` item 1. This section specifies what each arm has to log to answer it.

### Outcome variable per state

- **Access.** Time from a node entering a learner's frontier (first route response naming it) to first `open` event, and the fraction of frontier-eligible nodes ever opened at all, the engagement-rate variable Oreopoulos and Low 2026 (cited in PLAN.md section 3) show can gate every downstream effect to near zero if too low.
- **Awareness.** Recognition accuracy on a low-stakes item given at least one day after the `open` event, scored independent of the Check tool, since Awareness itself carries no model-graded signal to reuse as its own outcome measure.
- **Understanding.** Check tool verdict on the submitted explanation (support and not abstained and not low confidence), cross-scored by a human rater against the same rubric on a sampled subset, per the inter-rater procedure below; this is also RQ8's own "delayed unassisted post-test" variable when re-administered after a retention interval with the AI tools withdrawn.
- **Internalization.** Pass and fail on the sealed-pool transfer item, plus the teacher's approve and return decision as a second, independent rating of the same attempt; agreement between the automated grade and the teacher decision is itself an outcome, RQ3's misclassification-rate question.
- **Production.** Blind expert rating of accepted productions against the engine's own evidence tiers (RQ12), scored only on productions with `graph.productions.status = "accepted"`, never on `stage = "production"` alone, per section 1's submission-versus-acceptance distinction.

### Transfer-task construction rule for Internalization

An Internalization transfer item is built by construction, from a template skeleton plus a scenario wrapper, drawn from a sealed, held-out item pool the learner has never seen, and is multi-hop across the graph, requiring more than the one node just studied (system review section 3, "Understanding versus Internalization, in practice"; `learning/EPIC.md` Phase 2, "Generate transfer items by construction"). Three properties the pilot has to enforce, since none is checked in code today: exposure control, an item served to a learner is marked consumed and never re-served to that learner even across sessions, which needs a table this codebase does not yet have; distractor sourcing, wrong-answer options are drawn from a documented error model tied to the node's own common misconceptions, each call reusing that model instead of generating a fresh guess; and Bloom targeting, each item is tagged with which of Bloom revised's cognitive processes it tests (section 2's Bloom mapping above), so a pilot can report Internalization pass rates by cognitive process instead of as one undifferentiated number, closing part of OPEN-3 below.

### Inter-rater procedure for teacher judgments

`graph.teacher_reviews` (`supabase/migrations/20260910020000_research_os_teacher_reviews.sql`) has one `reviewer_id` column and no second rater, no blind-rating flag, and no agreement score anywhere in its schema, confirmed by reading the migration in full. The pilot needs a sampling rule and a disagreement procedure neither the schema nor `reviewer.ts` currently supports: a fixed fraction of every reviewer's `approved` and `returned` decisions, at minimum every `returned` decision given its higher stakes for the learner, routed to a second reviewer blind to the first reviewer's decision and reason; Cohen's kappa computed per reviewer pair on the sampled set; and a named resolution path, a third reviewer or the study's own PI, for any disagreement the kappa computation flags. None of this is a change to `stages.ts`'s transition logic; it is a second write path into `graph.teacher_reviews` this schema does not yet have a column for, listed as a schema gap below.

### Minimal logging schema

The full field-by-field contract lives in `src/lib/research-os/EVIDENCE-SCHEMA.md`, written alongside this paper so `ros-04` and `ros-06` can implement it without re-deriving it from this section. In outline, the workspace has to emit, per evidence event: which state transition function produced it, and both the state before and the state after; the full text of any learner-authored artifact judged, an explanation or a transfer-item answer, alongside the verdict; the model's full verdict, its result, its confidence, whether it abstained, its citations, and its feedback text, in full rather than as the result and confidence alone; which pooled item, by a stable item id, a transfer-item event answered, for exposure control; a session identifier grouping every tool call in one sitting, for the process-signal measures (attempt diversity, time on task) `RESEARCH-QUESTIONS.md` item 15 and PLAN.md section 4's teacher class view both need; and, for any teacher or reviewer judgment, the reviewer's id, a second rater's id and decision when sampled, and the resulting agreement flag.

### Current schema against that plan: the gaps

Checked directly against `src/lib/research-os/types.ts`'s `EvidenceEvent` interface, `src/lib/research-os/stages.ts`, and the `graph.learner_node_state`, `graph.productions`, and `graph.teacher_reviews` migrations:

- **No before-and-after stage pair on an event.** `EvidenceEvent` carries `kind`, `result`, `confidence`, `held`, `heldReason`, `note`, and `reviewerId`, never the stage the row was at before this event or the stage it moved to as a result. Reconstructing a learner's full stage-transition timeline from the evidence log alone requires re-running today's version of the transition rules over the log in order, which breaks silently the day those rules change, since old evidence rows carry no record of which rule version produced them.
- **No stored explanation, transfer-item answer, or transfer-item id.** `gradeExplanation` receives the learner's explanation text and `Check`'s citations and feedback string, and none of the three is written onto the evidence event; only `result` and `confidence` persist. The same is true of `onTransferItemAnswered`, which logs that an attempt happened with no record of which pooled item was served or what the learner answered. Neither an inter-rater audit nor an exposure-control check can run against data this codebase does not keep.
- **`abstained` is used to decide a transition and then discarded.** `GradeResult.abstained` drives `onCheckResult` and `onProbeCheckResult`'s branching directly, and `EvidenceEvent` has no `abstained` field to persist it. A later audit of RQ9, "does the check tool's abstain path fire when retrieval is weak," cannot be run against the stored evidence log alone; it would need every Check call re-run.
- **No inter-rater fields anywhere.** `graph.teacher_reviews` has exactly one `reviewer_id` per row. There is no second-rater id, no blind-sampling flag, and no agreement score column, the schema addition the inter-rater procedure above needs before it can run.
- **No session or attempt grouping.** Neither `graph.learner_node_state.evidence` nor `graph.productions` carries any field that groups events from one sitting together; every process-signal measure that depends on session-level aggregation (attempt diversity, time on task, tool-call sequencing) has to be reconstructed from timestamp proximity alone, an approximation rather than a ground truth.
- **A returned production leaves no corrective evidence event.** Named in section 1 and section 3: `onProductionSubmitted` raises `stage` to `production` at submission; the review route's production branch never calls `recordEvidence`, so a returned production is invisible in `graph.learner_node_state.evidence` and `stage` never reflects the rejection.
- **No live retention or proficiency field reaches a Research OS row at all.** Confirmed by the full-codebase search in section 3: `graph.learner_node_state` has a single `confidence real` column, set by no code path found in `stages.ts`, `db.ts`, or any `/api/research-os/*` route, so the "visible confidence" PLAN.md section 2 promises alongside every state has a column and no writer.

## 5. Open questions

Each item below is posed by a specific paper, per this paper's own mapping in section 2, and is distinct from the forty-nine questions already catalogued in `RESEARCH-QUESTIONS.md`; several sharpen an existing question there rather than replacing it.

**OPEN-1.** ICAP claims four ordered engagement modes are sufficient to predict learning outcomes; does Bucket's five-state model predict anything ICAP mode alone does not, or does it restate ICAP under new names with one extra floor and one extra ceiling added. Posed by Chi and Wylie 2014; sharpens `RESEARCH-QUESTIONS.md` item 1.

*Evidence added in batch three, complicates the framing:* Hidi and Renninger 2006 (`_intake/research-os-k12-literature/educational-methods/hidi-renninger-2006-four-phase-interest-model.md`) name a second, independently developed staged framework, four interest phases from situational trigger through self-sustained individual interest, that OPEN-1's own framing does not account for. The open question extends past whether the five states restate ICAP, to whether they restate, are independent of, or overlap this second competing staged model of engagement.

**OPEN-2.** SOLO's five levels are argued to form one ordered structural-complexity trait; do Bucket's five states, measured across many nodes for the same learner, fit one Rasch or IRT dimension the way SOLO's levels are argued to, or do Understanding and Internalization split into separable dimensions once measured at scale. Posed by Biggs and Collis 1982; this is `RESEARCH-QUESTIONS.md` item 28 restated against SOLO's own unidimensionality claim.

*Evidence added in batch three, supports the premise and complicates the outcome:* Hestenes, Wells, and Swackhamer 1992 (`_intake/research-os-k12-literature/educational-methods/hestenes-wells-swackhamer-1992-force-concept-inventory.md`) supply the field's own canonical example of a concept-level instrument built and repeatedly validated through exactly this Rasch or IRT process, supporting the premise that such a test is applicable here. Alonzo and Steedle 2009 (`_intake/research-os-k12-literature/educational-methods/alonzo-steedle-2009-force-motion-learning-progression.md`) complicate the likely outcome: three independent placement methods applied to a comparably sized five-level learning progression agreed for only a modest majority of students, with some student response patterns consistent with skipping a hypothesized level entirely, direct field evidence that the split-into-separable-dimensions risk this question names is a live one rather than a remote possibility.

**OPEN-3.** Bloom revised crosses six cognitive processes against four knowledge types in a two-dimensional grid; Bucket's Understanding state collapses both dimensions into one undifferentiated stage. Does separately tracking which knowledge type, factual, conceptual, procedural, a learner has reached at Understanding change what the state predicts, compared with treating Understanding as one bucket the way the shipped code does today. Posed by Anderson and Krathwohl 2001.

*Evidence added in batch three, complicates the framing:* Linn 2000 (`_intake/research-os-k12-literature/educational-methods/linn-2000-knowledge-integration-environment.md`) offers a third alternative to the binary this question poses between one undifferentiated bucket and Bloom revised's four knowledge types: a continuous knowledge-integration score built from how many ideas a learner has connected and how well contradictions between them are reconciled. Learners who reached the same knowledge type by this paper's own account still varied in integration score, evidence a knowledge-type label alone would not capture what Linn's framework measures.

**OPEN-4.** Perkins names several understanding-performance types beyond explanation and application; do justification, comparison and contrast, and generalization, none of which the shipped Check tool or transfer-item pipeline tests, add predictive power over the two performance types Bucket already tests, or does testing explanation and application alone already capture what those other performance types would add. Posed by Perkins 1993 and Wiske 1998.

*Evidence added in batch three, supports treating self-explanation as a measurable performance type:* Chi and colleagues 1989 (`_intake/research-os-k12-literature/educational-methods/chi-et-al-1989-self-explanations-study-examples.md`) supply a decades-old, hand-built scoring scheme for a performance type close to Perkins's own justification category, counting the inferences a learner generates while studying rather than the surface correctness of a final answer. Renkl 2002 (`_intake/research-os-k12-literature/educational-methods/renkl-2002-worked-out-examples-self-explanations.md`) extends this with a design answer for how a workspace hint should scaffold that performance type without collapsing into telling the learner the answer: a brief hint at a step's rationale raised self-explanation frequency, while a hint restating the step's own content added no benefit.

**OPEN-5.** Hambleton and Jones 1993 (`_intake/research-os-k12-literature/educational-methods/hambleton-jones-1993-ctt-vs-irt.md`) frame measurement validity as a property a construct earns through fit statistics and item-response modeling, a bar above face validity alone. The founder's original three-level model, Awareness, Explainable understanding, Internalized understanding, was never run through any such procedure before the five-state model expanded it. Does the expanded five-state model, once it clears the Rasch or IRT test OPEN-2 names, recover the founder's original three tiers as a coherent sub-structure, or does the expansion itself change what the middle and top tiers measure.

*Evidence added in batch three, supports and extends the bar:* Corcoran, Mosher, and Rogat 2009 (`_intake/research-os-k12-literature/educational-methods/corcoran-mosher-rogat-2009-learning-progressions-science.md`) support the premise that a validation procedure of this kind exists and applies to a claimed learner-progression model, and extend the bar past OPEN-2's Rasch or IRT test: a progression can be locally valid for one curriculum and assessment context without being valid past that context, a scope question the five-state model would still face even after clearing an IRT test. Hestenes, Wells, and Swackhamer 1992's finding that teacher judgment of understanding routinely overestimates measured performance sharpens the founder-tier question further, since the founder's own original three-tier model was set by judgment rather than by an instrument of this kind.

**OPEN-6.** Corbett and Anderson 1995 (`_intake/research-os-k12-literature/educational-methods/corbett-anderson-1995-knowledge-tracing.md`) and Piech and others 2015 (`_intake/research-os-k12-literature/educational-methods/piech-2015-deep-knowledge-tracing.md`) both argue that the choice of knowledge-tracing method changes prediction accuracy in ways a coarse binary or ordinal state cannot capture. Section 3 establishes that no Research OS state transition reads an FSRS or IRT signal today. Once the join section 3 describes is built, does adding live retrievability change the timing of the Awareness-to-Understanding and Understanding-to-Internalization transitions enough to matter for the pilot's own outcome measures, or does the current open-event-and-Check-verdict pair already predict as well as a retrievability-augmented version would.

**OPEN-7.** Sztajn and others 2012 (`_intake/research-os-k12-literature/educational-methods/sztajn-et-al-2012-learning-trajectories.md`) show that a subject's logical prerequisite order and the developmental path students take through it can diverge, and that placing a student on that path requires ongoing formative judgment rather than one fixed rule applied uniformly. Given that Bucket's teacher contest path exists today only for the Internalization gate and the production accept and reject decision, both narrower than "contest any state" section 2's PLAN.md mapping table promises, at what rate would a teacher, given a general contest control over every one of the five states rather than only these two gates, disagree with the graph's own classification, and does that disagreement rate track the trajectory-versus-prerequisite divergence Sztajn and others document in mathematics.

*Evidence added in batch three, supports the premise and supplies a comparison baseline:* Alonzo and Steedle 2009 (`_intake/research-os-k12-literature/educational-methods/alonzo-steedle-2009-force-motion-learning-progression.md`) support the premise directly, a field-tested case of exactly this trajectory-versus-prerequisite divergence, measured with three independent methods on a comparably sized progression, with a disagreement rate that was not small. Jönsson and Svingby 2007 (`_intake/research-os-k12-literature/educational-methods/jonsson-svingby-2007-scoring-rubrics-reliability-validity.md`) supply a comparison baseline for reading whatever contest rate a pilot measures: even well-built rubrics with benchmark examples and rater training leave a residual disagreement rate among human raters, so a nonzero teacher-contest rate should not by itself be read as evidence the classifier is broken.

No claim in this paper goes past what `src/lib/research-os/` and its migrations ship on `main` today, or what the cited papers themselves report. Every framework citation in section 2 was verified by DOI or ISBN resolution before this paper was written; the four new papers used here that had no existing intake card, ICAP, SOLO, Bloom revised, and the Perkins and Wiske pair, now have one each under `_intake/research-os-k12-literature/educational-methods/`.
