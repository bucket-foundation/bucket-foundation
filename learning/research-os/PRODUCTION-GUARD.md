# Research OS for K-12: The Production Provenance Guard

**Status:** shipped, production guard bead · **Date:** 2026-09-10 · Reads against `learning/research-os/WORKSPACE.md`, `src/lib/research-os/EVIDENCE-SCHEMA.md`, `src/app/api/research-os/production/route.ts`, `src/app/api/research-os/review/route.ts`, `src/app/research-os/review/page.tsx`, `src/lib/research-os/production-guard.ts`, `src/lib/research-os/canon-link.ts`, and `GOVERNANCE.md`'s "Canon sign-off" section.

The Production form (`WORKSPACE.md` section 4) is where a learner's claim, evidence, sources, and transfer proof leave the workspace and enter a teacher's queue. Nothing in Phase 0 checked whether a cited source was real, whether a claim echoed work already on file, or whether a claim that reached the internalization tier carried any rebuttal of its own. This bead adds that check, four rules and a review-queue surface, none of which pay anyone: `GOVERNANCE.md`'s own rule ties payment to canon acceptance, a separate event from a Production's own acceptance, and this bead computes an eligibility signal toward that, no payment code.

## 1. Quote matching

Every source line in a Production's `sources` field is checked against this learner's own `"quote"`-kind evidence events (`src/lib/research-os/stages.ts`'s `onQuoteReturned`, written whenever the Quote tool returns a real curated passage rather than the `"summary"` fallback, see `WORKSPACE.md` section 2). A source verifies when its own text carries, verbatim after whitespace/case normalization, the `locator` of one of those events (`src/lib/research-os/production-guard.ts`'s `checkSourceProvenance`). Sources are free text, the Production form's "sources, one per line" field, so substring containment on the locator string is the check this rule can make. The workspace's own "sources I have quoted" list carries an "add to sources" button that inserts the exact `citation (locator)` line a source needs to verify; a learner who uses it passes automatically, one who types a source from memory does not.

The result is stored per source as `{text, verified}` in `graph.productions.source_provenance`, computed once at submit time by `/api/research-os/production`'s POST and never recomputed by the review route. **A Production with any unverified source cannot reach `status: "accepted"`**: `/api/research-os/review`'s POST refuses an `"approved"` decision on it with a 409 (`unverified_sources_block_accept`), and the review page disables its own approve button the same way, with a template return note (`unverifiedSourceReturnNote`) a reviewer can send as-is or edit. `"returned"` stays available regardless.

## 2. Duplicate detection

On submit, a Production's claim text is compared, by normalized token overlap, against three populations: this learner's own prior Productions, other learners' `accepted` Productions in the same class (`graph.class_members`), and canon claim texts (a build-time JSON of canon claim summaries, `scripts/research-os/ingest/canon-claims.ts` reading every `bucket-canon/**/primary-papers.yaml` record via `src/lib/canon-primary.ts`'s existing loader). The comparison is the same lexical Jaccard-similarity approach `tools/hypothesis-engine/hte/novelty.py` already uses for the hypothesis engine's own write-back path, ported to TypeScript (`production-guard.ts`'s `tokenize`/`jaccardOverlap`): no external model, no network, deterministic, no stop words dropped.

The single closest match at or above `DUPLICATE_OVERLAP_THRESHOLD` (0.6) writes a `duplicate_flag` on the row, `{matchId, matchOrigin, score}`; below that, or with no candidates at all, `duplicate_flag` is `null`. **Duplicate detection never blocks submission.** It is stored and shown beside the queued Production (task item 5) for a reviewer's own read; the flag names the closest match, it does not adjudicate it.

## 3. Counter-evidence

`graph.productions.counter_evidence` (`[{text}]`) is optional in Phase 0, matching the same free-text discipline `evidence` and `sources` already carry. It becomes **required at submission** once the learner's own stage, at the moment of submitting, had already reached Internalization (`production-guard.ts`'s `requiresCounterEvidence`, `stageAtLeast(fromStage, "internalization")`): Osborne 2010's own case for argumentation is that the reasoning benefit comes from defending a claim against a challenge, so a claim that survived a teacher-approved transfer item is the point at which asking for a rebuttal earns its place. A submission that needs counter-evidence and has none is refused with 400, before any row is written; a `counter_evidence_required` snapshot is stored alongside the row regardless, so the review queue can surface "missing counter-evidence" for any row written by a path other than this route (a pre-guard row, a future direct write) without re-deriving `fromStage`.

## 4. Incentive eligibility

`graph.productions.production_incentive_eligible` is a boolean, computed and stored only at the moment a reviewer's decision flips a Production's `status` to `"accepted"` (`production-guard.ts`'s `computeIncentiveEligible`). It reads `true` only when the target node's linked canon record (`graph.nodes.provenance.paper_id`, the same link `scripts/research-os/ingest/canon-import.ts` already writes) carries a raw `provenance_signoff` value starting with `"approved"` (`canon-link.ts`'s `lookupCanonSignoff`, reading the UNFILTERED record set, since `src/lib/canon-primary.ts`'s own `loadPrimaryPapers` deliberately excludes a pending or rejected record before a caller could read its signoff back out). A pending, rejected, missing-signoff, or no-canon-link Production, and every still-submitted or returned one, reads `false`.

`GOVERNANCE.md`'s "Canon sign-off" section states the underlying rule this column exposes: "Approval is the named approver replacing a `pending: <name>` value with their own confirmation." This bead writes no payment code and reads no wallet, ledger, or Viatika API; it stores the eligibility signal a future payout pass would read instead of re-deriving one.

## 5. What a teacher sees

`/research-os/review`'s own page shows, beside each queued Production: an unverified-source list (with a "use unverified-source template" button that fills the return-reason field), a duplicate-match line naming the closest match's origin and overlap percentage, and a missing-counter-evidence warning at the internalization tier. Approve is disabled, client-side and server-side both, while any unverified source is present; every other flag is informational, visible but never blocking.

## 6. What is logged

`graph.productions.source_provenance`, `duplicate_flag`, `counter_evidence`, and `counter_evidence_required` are written once, at submit time, by `/api/research-os/production`'s POST. `production_incentive_eligible` is written once, at accept time, by `/api/research-os/review`'s POST. Every `teacher_reviews` row and every `learner_node_state.evidence` event this bead's own writes touch follow the same append-only, audit-trail discipline the rest of Research OS already keeps (`EVIDENCE-SCHEMA.md`); nothing here removes or edits a prior entry. New columns and their retention rule are inventoried in `learning/research-os/compliance/DATA-INVENTORY.md`.
