# Research OS for K-12: Data Inventory

Bead `ros-07`, minors compliance pack part A. Every table and jsonb field in this Supabase project that can hold a learner's data, its purpose, its legal basis, its retention rule, and whether the product needs it to function. Source tables: `supabase/migrations/20260910000000_research_os_graph.sql`, `20260910010000_research_os_engine_bridge.sql`, `20260910010000_research_os_prereq_ancestor.sql`, `20260910020000_research_os_teacher_reviews.sql`, `20260910030000_research_os_edge_confidence.sql`, `20260910030100_research_os_edge_flags.sql`, `20260910040000_research_os_privacy_consent.sql`, `20260612000000_academy_progress.sql`, `20260626000000_academy_credentials.sql`, plus `src/lib/research-os/EVIDENCE-SCHEMA.md` for the `evidence` jsonb contract. Legal basis language follows `_intake/research-os-k12/04-compliance-distribution.md` sections 1 and 2.

Scope note: this inventory covers Research OS (the `graph` schema) and Bucket Academy (the `bucket` schema) together, since both share the same `auth.users` identity. A learner's data footprint spans both surfaces the moment they hold one account, so a deletion or export request that touched only `graph.*` would not honor the request.

Out of scope for this pass, named here so it is not silently missing: a roster or `classes` table (planned for `ros-06`, absent from the schema as of this writing, see the `#### Not yet in the schema` note at the end of this file) and any district- or school-level record (that data belongs to the district under its own DPA, per the compliance plan's FERPA section).

## Free-Text Fields a Child May Have Written

This section names the retention and deletion rule for text a learner (who may be a minor) typed themselves. Three fields carry it, per `src/lib/research-os/EVIDENCE-SCHEMA.md`'s evidence contract and `graph.productions`'s own columns:

1. **`graph.learner_node_state.evidence[].learnerText`**: the learner's explanation on a `check` event, or their answer on a `transfer_item` event.
2. **`graph.learner_node_state.evidence[].note`**: an optional free-form note on any evidence event.
3. **`graph.productions.claim`**, **`.evidence` (the quote array's own notes)**, and **`.transfer_proof`**: the learner's claim text, the evidence they attached to it, and their Internalization-stage transfer answer.

**Retention rule**: this text lives exactly as long as the row containing it (see the retention column above), and is deleted the moment that row is deleted, whether by the learner's own account-level delete request or, once part B's time-based retention policy exists, by a scheduled purge. No separate copy is kept. `graph.teacher_reviews.reason` is adjacent but distinct: it is teacher-authored text about a learner, covered in the row below.

**Not learner-authored text**, named so it is not confused with the above: `graph.teacher_reviews.reason` (a teacher's own words), `graph.learner_profiles.consent_source` (an operator's short note on how consent was obtained, e.g. an NDPA exhibit reference or a VPC vendor confirmation id), and `graph.nodes` / `graph.edges` content (seeded curriculum, canon-bridge, or engine-authored, never learner-authored at Phase 0, see "Not learner data" below).

## Not learner data

| Table | Why it is out of scope |
|---|---|
| `graph.nodes` | Curriculum and canon content. Has a `created_by` column in its schema, but a full-codebase search (`grep -rn "created_by" src/ scripts/`, 2026-09-10) found no write path in Research OS code that ever sets it; every Phase 0 node is seeded or engine-authored, never learner-authored. Flagged here as a **dormant column**: if a future Phase 1+ feature lets a learner or teacher author a node directly, that write path needs its own data-minimization and deletion review before it ships, this inventory does not cover it today. |
| `graph.edges` | Structural relationships between nodes. No learner reference. |
| `graph.prereq_ancestor` | A derived cache of `graph.edges`, rebuilt from it. No learner reference. |
| `public.research_os_productions_outbox` | Deliberately has **no** `learner_id` column, by explicit design choice recorded in `20260910010000_research_os_engine_bridge.sql`'s own header: "a pseudonymous-but-real user id and a learner's own scratch text out of a table a second process reads." It does copy `claim`, `evidence`, and `sources` from an *accepted* production, which is the same free text named above, mirrored for the hypothesis engine's own read path. It is not independently deletable by learner id (there is no column to filter on), but it does not need to be: its `id` column is a foreign key to `graph.productions.id` with `on delete cascade`, so deleting the source production (which every delete request does) removes the mirror automatically. **Caveat, stated plainly rather than glossed over**: if the engine has already read an outbox row and derived a downstream hypothesis or node from it before the learner's delete request lands, that downstream engine artifact lives outside this Supabase project entirely (`tools/hypothesis-engine/`) and is not touched by this route. A production's citation-payment and public-attribution consequences, once it has been cited and paid, stand even after a later deletion request, the same way an already-paid real-world royalty stays paid despite a later privacy request; this is an inherent limit of "delete my data" once an action has already had a real-world effect. |

## Data minimization notes

- `graph.learner_profiles.birth_year_bucket` stores a three-value bucket (`under13` / `13to17` / `18plus`), never a birth date, exact age, or grade level. This is the coarsest fact `requireConsent` needs to make its decision; a more precise value would be collecting more than the activity requires, the exact thing COPPA's data-minimization requirement (compliance plan section 1) asks a product to avoid.
- `graph.privacy_events.learner_id_hash` stores a one-way sha256 digest of a learner id, never the raw id, so the audit trail proving an export or delete happened cannot itself be used to look up which learner it was about without already knowing the id to check against.
- `bucket.academy_profiles` already ships with "no email, no score/rating" as a stated design constraint (its migration's own header); this inventory carries that constraint forward rather than loosening it.

#### Not yet in the schema

A `classes` or roster table does not exist in this branch as of 2026-09-10 (confirmed: no migration or code reference to a `classes` table anywhere in this repo). `ros-06`'s teacher class view is the bead expected to introduce it. Once it ships, it will need its own row in this inventory (a roster table holds a different kind of PII, a teacher's list of which named students are in their class, potentially without the students' own IDs being present in the roster row at all, which is a different minimization question than the tables above) and its own entry in `PRIVACY_TABLES` (`src/lib/research-os/privacy.ts`) if it turns out to hold rows keyed by learner id.
