# Research OS for K-12: Data Inventory

Bead `ros-07`, minors compliance pack part A. Every table and jsonb field in this Supabase project that can hold a learner's data, its purpose, its legal basis, its retention rule, and whether the product needs it to function. Source tables: `supabase/migrations/20260910000000_research_os_graph.sql`, `20260910010000_research_os_engine_bridge.sql`, `20260910010000_research_os_prereq_ancestor.sql`, `20260910020000_research_os_teacher_reviews.sql`, `20260910030000_research_os_edge_confidence.sql`, `20260910030000_research_os_classes.sql`, `20260910030100_research_os_edge_flags.sql`, `20260910040000_research_os_privacy_consent.sql`, `20260910050000_research_os_roster.sql`, `20260910070000_research_os_check_attempts.sql`, `20260612000000_academy_progress.sql`, `20260626000000_academy_credentials.sql`, plus `src/lib/research-os/EVIDENCE-SCHEMA.md` for the `evidence` jsonb contract. Legal basis language follows `_intake/research-os-k12/04-compliance-distribution.md` sections 1 and 2.

Scope note: this inventory covers Research OS (the `graph` schema) and Bucket Academy (the `bucket` schema) together, since both share the same `auth.users` identity. A learner's data footprint spans both surfaces the moment they hold one account, so a deletion or export request that touched only `graph.*` would not honor the request.

Out of scope for this pass, named here so it is not silently missing: any district- or school-level record (that data belongs to the district under its own DPA, per the compliance plan's FERPA section). A roster table (`graph.classes` / `graph.class_members`) landed on `main` via `ros-06` after this inventory's first pass; both are covered below, `graph.classes` in "Not learner data" and `graph.class_members` in the learner-keyed table below it. The `ros-06` follow-on roster sync (`learning/research-os/ROSTER.md`) added `source_system`/`sourced_id` columns to `graph.classes` and `graph.learner_profiles`, and a new `graph.reviewer_candidates` table, covered in the same two sections below.

## Free-Text Fields a Child May Have Written

This section names the retention and deletion rule for text a learner (who may be a minor) typed themselves. Three fields carry it, per `src/lib/research-os/EVIDENCE-SCHEMA.md`'s evidence contract and `graph.productions`'s own columns:

1. **`graph.learner_node_state.evidence[].learnerText`**: the learner's explanation on a `check` event, or their answer on a `transfer_item` event.
2. **`graph.learner_node_state.evidence[].note`**: an optional free-form note on any evidence event.
3. **`graph.productions.claim`**, **`.evidence` (the quote array's own notes)**, and **`.transfer_proof`**: the learner's claim text, the evidence they attached to it, and their Internalization-stage transfer answer.
4. **`graph.check_attempts.explanation`**: the same explanation text as item 1 above, held here only for the short window between a Check's phase-1 grade and its phase-2 reveal (see the learner-keyed table above); the row, and this text with it, is gone the moment it is revealed or swept by the 24-hour hard expiry.

**Retention rule**: this text lives exactly as long as the row containing it (see the retention column above), and is deleted the moment that row is deleted, whether by the learner's own account-level delete request or, once part B's time-based retention policy exists, by a scheduled purge. No separate copy is kept. `graph.teacher_reviews.reason` and `graph.productions.notes[].reason` are adjacent but distinct: both are teacher-authored text about a learner, covered in the rows above.

**Not learner-authored text**, named so it is not confused with the above: `graph.teacher_reviews.reason` and `graph.productions.notes[].reason` (a teacher's own words), `graph.learner_profiles.consent_source` (an operator's short note on how consent was obtained, e.g. an NDPA exhibit reference or a VPC vendor confirmation id), and `graph.nodes` / `graph.edges` content (seeded curriculum, canon-bridge, or engine-authored, never learner-authored at Phase 0, see "Not learner data" below).

## Not learner data

| Table | Why it is out of scope |
|---|---|
| `graph.nodes` | Curriculum and canon content. Has a `created_by` column in its schema, but a full-codebase search (`grep -rn "created_by" src/ scripts/`, 2026-09-10) found no write path in Research OS code that ever sets it; every Phase 0 node is seeded or engine-authored, never learner-authored. Flagged here as a **dormant column**: if a future Phase 1+ feature lets a learner or teacher author a node directly, that write path needs its own data-minimization and deletion review before it ships, this inventory does not cover it today. |
| `graph.edges` | Structural relationships between nodes. No learner reference. |
| `graph.prereq_ancestor` | A derived cache of `graph.edges`, rebuilt from it. No learner reference. |
| `graph.classes` | A reviewer's own roster object (`name`, `reviewer_email`), added by `ros-06`; the `ros-06` follow-on roster sync added `source_system`/`sourced_id`, naming which OneRoster/Clever/ClassLink class this row mirrors. Holds the reviewer's email; a learner's own membership in it is the separate `graph.class_members` row, covered in the learner-keyed table above. `reviewer_email` is the one piece of PII here, and it belongs to a teacher's own account, outside this bead's scope (a *learner's* export/delete rights); a future compliance pass on staff/reviewer data would need its own inventory row. |
| `graph.reviewer_candidates` | A staging list of teachers a roster sync has seen (`source_system`, `sourced_id`, `email`, `name`, `status`), added by the `ros-06` follow-on roster sync (`learning/research-os/ROSTER.md`). Syncing a roster never grants review access; `RESEARCH_OS_REVIEWER_EMAILS` stays the only gate, and this table only ever feeds the human decision to add an email to that env var. Staff contact information, the same posture `graph.classes.reviewer_email` already has above; out of a learner's own export/delete rights. RLS is enabled with no anon/authenticated policy at all (service-role only), matching `graph.privacy_events`. |
| `public.research_os_productions_outbox` | Deliberately has **no** `learner_id` column, by explicit design choice recorded in `20260910010000_research_os_engine_bridge.sql`'s own header: "a pseudonymous-but-real user id and a learner's own scratch text out of a table a second process reads." It does copy `claim`, `evidence`, and `sources` from an *accepted* production, which is the same free text named above, mirrored for the hypothesis engine's own read path. It is not independently deletable by learner id (there is no column to filter on), but it does not need to be: its `id` column is a foreign key to `graph.productions.id` with `on delete cascade`, so deleting the source production (which every delete request does) removes the mirror automatically. **Caveat, stated plainly rather than glossed over**: if the engine has already read an outbox row and derived a downstream hypothesis or node from it before the learner's delete request lands, that downstream engine artifact lives outside this Supabase project entirely (`tools/hypothesis-engine/`) and is not touched by this route. **Required manual call**: `hte purge --production <id>` (`tools/hypothesis-engine/hte/purge.py`, `tools/hypothesis-engine/docs/PRIVACY.md`) reaches the four engine-side landing spots a delete request cannot, run directories, the LLM response cache, bridge exports, and feed402 write-back envelopes under `public/research/hypotheses/`, keyed by production id. It never touches `bucket-canon/`: a signed-off canon card and its ingestion-index entry stand after purge, the same way a paid citation stands. This call is not yet wired into `POST /api/research-os/privacy`; until it is, an operator runs it by hand for every production id a delete request names. A production's citation-payment and public-attribution consequences, once it has been cited and paid, stand even after a later deletion request, the same way an already-paid real-world royalty stays paid despite a later privacy request; this is an inherent limit of "delete my data" once an action has already had a real-world effect. |

## Data minimization notes

- `graph.learner_profiles.birth_year_bucket` stores a three-value bucket (`under13` / `13to17` / `18plus`); the column itself never holds a birth date, an exact age, or a grade level. This is the coarsest fact `requireConsent` needs to make its decision; a more precise stored value would be collecting more than the activity requires, the exact thing COPPA's data-minimization requirement (compliance plan section 1) asks a product to avoid. The `ros-06` follow-on roster sync (`learning/research-os/ROSTER.md`) is a second path that can set this column, mapped from a OneRoster grade code through a fixed table; it reads no birth date field, since OneRoster's own CSV bundle carries none for this importer to read.
- `graph.reviewer_candidates` carries no student data at all: `email` and `name` are a teacher's own contact information, and `source_system`/`sourced_id` are the roster row's own external id. The roster importer drops every other `users.csv` column at parse time (username, password, phone, sms, identifier, and the rest); see `learning/research-os/ROSTER.md`, "What is discarded," for the full list.
- `graph.privacy_events.learner_id_hash` stores a one-way sha256 digest of a learner id, never the raw id, so the audit trail proving an export or delete happened cannot itself be used to look up which learner it was about without already knowing the id to check against.
- `bucket.academy_profiles` already ships with "no email, no score/rating" as a stated design constraint (its migration's own header); this inventory carries that constraint forward rather than loosening it.
- `graph.class_members` carries exactly two columns (`class_id`, `learner_id`), matching `20260910030000_research_os_classes.sql`'s own stated scope, "a roster of exactly two columns' worth of information, deliberately."
