## Drift

1. **Chat tool schemas vs feed402 search params, DRIFT** *(severity: medium)*
 - `src/app/api/chat/route.ts:55-66` declares `feed402_search_patents` with only `{ query, limit }`.
 - The actual `/patents/search` route accepts `q, class, from, to, jurisdiction, lat, lng, radius, limit` (`routes/patents.ts:380-390`). The chat agent has no way to filter by CPC class, date range, or jurisdiction, leaving the most useful query power dark.
 - Same schema is used identically for `feed402_search_pubmed` and `feed402_search_openalex`, both of which presumably also have richer params on the gateway side.
 - **Fix:** widen `feed402_search_patents` input_schema to include `cpc_class?, from?, to?, jurisdiction?` (mirror server-side names). Plumb through `feed402-client.ts:72-75` (currently also drops everything but q+limit).

2. **feed402-client base URL vs server route prefix, DRIFT** *(severity: medium)*
 - Client posts to `/pubmed/search`, `/openalex/search`, `/patents/search` (`feed402-client.ts:62-75`).
 - Patents routes ARE at `/patents/*`. PubMed/OpenAlex routes are not part of bkt-zx6, confirm the existing feed402 server (`server.ts`) mounts them. If those routes don't exist yet, the chat will 404 on those tools at runtime.
 - **Fix:** verify in `viatika-x402-data-standard/server.ts` that `/pubmed/*` and `/openalex/*` mounts exist; if not, file follow-up bead.

3. **Citation envelope shape mismatch, DRIFT** *(severity: medium)*
 - `feed402-client.ts:8-26` `CitationEnvelope` has shape `{ citation: {...}, payment: {...}, meta: {...} }` with `citation.title/authors/year/snippet/doi`.
 - Actual feed402 envelope per SPEC §3 + `routes/patents.ts:399-409` is `{ data, citation, receipt }` where `citation` is a `CitationSource` `{ type, source_id, provider, retrieved_at, license, canonical_url }`, no `title/authors/year/snippet/doi` fields. `data.rows` carries the title/abstract.
 - **Fix:** rewrite `CitationEnvelope` in `feed402-client.ts` to match SPEC §3 envelope (`data` + `citation` + `receipt`). The chat tool will otherwise see `undefined` for title/authors and emit ungrounded text.

4. **`getCitationEnvelope` route does not exist on feed402, DRIFT** *(severity: medium)*
 - `feed402-client.ts:77-80` calls `GET /citation?url=...` for $0.01.
 - No such route is mounted by `routes/patents.ts` and SPEC.md §6.1 doesn't define one. The chat tool `feed402_get_citation_envelope` (`route.ts:67-78`) will 404.
 - **Fix:** either delete the tool or add a `/citation?url=` resolver on the feed402 side; minimum-viable v1 is to delete the tool from `TOOLS` array, the search responses already carry full citation envelopes inline.

5. **Postgres Secret placeholder, DRIFT** *(severity: low)*
 - `postgres.yaml:20` has `POSTGRES_PASSWORD: "${POSTGRES_PASSWORD}"`, `kubectl apply` will store the literal string `${POSTGRES_PASSWORD}` if the README workflow isn't followed exactly.
 - The README tells the operator to create the Secret separately first, but the literal placeholder in the manifest is still a footgun if someone naively `kubectl apply -f postgres.yaml` without reading.
 - **Fix:** remove the `Secret` stanza from `postgres.yaml` entirely (the README already shows the canonical `kubectl create secret` invocation), OR replace `stringData` with a comment that says "create out-of-band; this stanza intentionally absent."

6. **ESPACENET URL pattern for EP, DRIFT** *(severity: low)*
 - `routes/patents.ts:306` builds `https://worldwide.espacenet.com/patent/search/publication/${g.patent_id}`. The actual Espacenet deeplink format is `.../patent/search?q=pn%3DEP1234567` or the publication number must be CC-prefixed (e.g. `EP1000000`).
 - **Fix:** use `https://worldwide.espacenet.com/patent/search/publication/EP${id}` or switch all jurisdictions to `https://patents.google.com/patent/${jurisdiction}${id}` for v1 simplicity (Google Patents resolves EP/WO/JP/KR/CN cleanly).

## Blockers

1. **`Citation` envelope is singular, but `data.citations[]` is shoved in unsafely, BLOCKER** *(severity: high)*
 - `routes/patents.ts:408` does `(env.data as Record<string, unknown>).citations = citations;`, this trades type-safety for a side-channel and the chat client has no awareness it should look there.
 - `Envelope` in `types.ts` declares `citation: CitationSource` (singular). The SPEC §3 self-reference at `routes/patents.ts:404-406` even acknowledges this is non-canonical.
 - **Impact:** any agent that grounds on `envelope.citation` only (the spec-correct path) will see only the FIRST result's citation, despite paying for N rows. The chat agent will then misattribute results 2-N to the first row's source, a citation-correctness violation, which is the entire point of feed402.
 - **Fix:** either (a) promote `Envelope.citation` to `CitationSource | CitationSource[]` in `types.ts` and update SPEC.md §3 (recommended; SPEC author already flagged this in the inline comment), or (b) emit a separate envelope per row and have the route return an array of envelopes for multi-row responses.

2. **PostGIS install at runtime is fragile, BLOCKER** *(severity: high)*
 - `postgres.yaml:28-35` uses `apt-get install postgresql-16-postgis-3` from `docker-entrypoint-initdb.d/00-postgis.sh`. This runs **only on first init**. If the StatefulSet pod is ever rescheduled to a new node *and* the PVC is preserved, the binary won't be on the new container image and `CREATE EXTENSION postgis` (already executed once) will succeed, but any pg_upgrade or extension reload will fail with "could not access file 4".
 - More immediately: `apt-get update` from inside the pgvector image at boot is a network-dependent step; if the Hetzner node has firewall'd outbound or apt mirrors are slow, the pod will Fail readiness.
 - **Fix:** build a custom image `agfarms/postgres-postgis-pgvector:pg16` with both extensions baked in, push to Docker Hub (alongside `farmera/nucleus`), and reference that image. The README already flags this TODO at line 84-85, promote it to a bead.
 - **Workaround for v1:** add a `postStart` lifecycle hook that runs the apt-install on every pod start (idempotent if already installed) so reschedules don't break.

3. **NextAuth requires an Adapter for EmailProvider, BLOCKER** *(severity: high)*
 - `src/lib/auth.ts:6` uses `EmailProvider` from `next-auth/providers/email` with `session: { strategy: "jwt" }` and **no adapter**.
 - NextAuth v4 requires a database adapter when using EmailProvider, the magic-link flow needs a `verification_tokens` table to persist the token between request-link and click-link. JWT-only sessions do NOT skip this requirement; the comment at `auth.ts:8-10` is incorrect.
 - **Impact:** `/api/auth/signin/email` will throw at runtime, blocking all chat access.
 - **Fix:** add a Supabase adapter (`@auth/supabase-adapter`) wired to the existing `SUPABASE_*` env vars OR ship a Prisma adapter pointed at the new Postgres in `bkt-pf0` (preferred, keeps all bucket auth on one substrate). File as bead bkt-q7k+3 (already TODO'd in code at line 8) and gate `NEXT_PUBLIC_CHAT_ENABLED=true` on its completion.
